# 0026 用量与预算：计量是事实（进日志），超限是结果（结构化收尾）

- 日期：2026-10-14
- 阶段：P3_Coding `_03_Usage_Budget`（P3 第三个阶段）
- 状态：已采纳

## 背景

到 `_02` 为止，系统不知道"一次对话花了多少 token"。三个现实需求逼出这一阶段：

1. **成本可见**：DeepSeek 按 token 计费，用户需要知道每轮花多少（真实数据：
   一次"你好"约 1900 tokens——因为每步都要重发完整历史）；
2. **预算可控**：`_02` 已取消默认步数上限（长程任务不截断），代价是"跑飞了
   没有刹车"。需要一个按用量而非步数的刹车；
3. **流式的账是瞎的**：`_02` 的流式路径拿不到完整 `LLMResponse`（聚合发生在
   循环里），用量必须单独接出来——否则一开流式，账本永远是 0。

## 决策

**1) `Usage` 成为一等词汇，支持累加。**

    Usage(prompt_tokens, completion_tokens)        既有
    usage.total_tokens                             新增（预算按它算）
    usage_a + usage_b                              新增（turn 内多次调用求和）

**2) 用量是"事实"，进会话日志；增量是"过程"，不进。**

新增两类事件：`usage/step`（每次调用的用量）与 `budget/exceeded`（超限）。
这与 `_02` 的 `step_delta`（瞬态、不进日志）形成明确对照：

    step_delta    过程（怎么吐出来的）→ 只给观察者
    usage/step    事实（真花了多少）  → 进日志，可对账、可 resume

理由：用量很小（几个整数），但它是**核算依据**——预算、成本报表、跨进程恢复
都要读它。而增量很大（一条回复几十行），且可由聚合结果重建。

**3) 超预算是"结果"，不是异常。**

turn 以 `budget_exceeded` 收尾：`TurnResult.status` 表明原因、`final_text` 保留
已生成的部分、`usage` 如实带回。调用方据此决定下一步。检查点刻意放在
"判定完成"**之前**——超预算的 turn 不该再假装 `done`，否则调用方看到"正常完成"
却不知道这次已经花超了。

**4) 流式路径的用量单独接。**

流式下用量在两个地方容易丢：
- **帧对象上**（不在 `delta` 上）：带 usage 的那一帧 `choices` 通常为空，
  必须在处理 choices 之前先取；
- **默认不上报**：OpenAI 兼容协议要显式传 `stream_options={"include_usage": True}`。

两处都实测踩到（账本恒为 0）。现在 `chunk_usage_from_frame` 负责取帧级 usage，
`DeepSeekProvider.stream` 负责开启上报；流式聚合把 usage 放进末帧、
`llm` 插件的代理随 `llm/response` 广播出去（否则账本对流式仍是瞎的）。

**5) 账本按 (会话, turn) 聚合，不是只按 turn。**

turn 号**每会话独立编号**。只按 turn 聚合会把不同会话的同号 turn 并成一条
（实测：两个会话的 turn 1 显示成"turn 1 有 4 次调用，9791 tokens"）。
现在 `UsageRecord` 带 `session`，账本与页面的明细都是"会话 · turn"。

**6) `token-usage` 是一个插件，三件产出。**

    UsageLedger             内存账本（订阅 llm/response 累计）
    usage_stats 工具         模型可自查（预算敏感场景它得知道自己花了多少）
    / 与 /api/usage          人可看；JSON 带 CORS 头，供主界面跨源读

**挂载契约**（与主界面的对接点，走通用规则而非特例）：

    /api/ledger 的 endpoints["token-usage"] → http://127.0.0.1:8767/
    主界面据此把「📊 Token 用量」按钮挂到顶栏，iframe 打开页面

主界面**不认识**这个插件，只认 endpoints 里有地址的服务——所以任何"自报地址"
的服务都能被挂上去（webui 自己也在 endpoints 里）。

## 备选与排除理由

1. **把用量写进 `step_delta` 一样当瞬态处理**。排除：用量是对账依据，
   丢了就没法核算；而且它很小，进日志不构成负担。
2. **超预算抛异常**。排除：超预算是**业务结果**而非程序错误——调用方需要
   拿到"已用多少、部分回答是什么"来决定后续（提醒用户充值 / 降级模型 / 停止），
   异常会把这些信息变成 traceback。
3. **预算按"每步"而不是"每 turn"检查**。排除：用户关心的是"我这一问花了多少"；
   按 turn 累计更贴近直觉，也允许单步大用量（如长上下文）而不误伤。
4. **账本落盘到会话日志里做持久读视图**。暂缓：`usage/step` 已经在日志里，
   需要历史报表时从日志投影即可；账本保持内存态（与"每次启动重新装配"一致）。

## 后果

- **收益**：用量可见（页面 + JSON + 工具三条路）；预算可控（结构化超限收尾）；
  流式路径的账不瞎；日志里有用量事件可对账。
  真实数据实测：alpha 会话 turn 1 = 1920 tokens、beta 会话 turn 1 = 3946 tokens
  （同号 turn 正确分开）。
- **约束与已知边界**：
  1. **账本只在内存**：进程重启归零（历史要从会话日志的 `usage/step` 投影）；
  2. **预算是"每 turn"的**，没有"整会话总额"或"按天"的配额；
  3. 页面的"占比"条按最大 turn 归一化，不是绝对值视图；
  4. **流式 usage 依赖 provider 上报**：本地模型或某些网关可能不返回，此时按 0 计
     （不崩、不虚报）。
- **债务与后续**：
  1. 会话级 / 全局级配额（`_05` 任务管理可能需要）；
  2. 真实模型名没记进账本（`model` 字段为空）——`llm/response` 的 request 里
     有 `model`，但流式路径构造的轻量响应不带，需要时补；
  3. 页面未做时间维度（按小时/按天的曲线）。
