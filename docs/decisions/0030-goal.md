# 0030 持久目标：状态由日志派生，续跑有三道闸门

- 日期：2026-10-14
- 阶段：P3_Coding `_06_Goal`（P3 第六个阶段；PLAN 原定 `_06_Tasks` 的 goal 部分，
  按用户要求先做 goal、todo 清单留待后续）
- 状态：已采纳

## 背景

用户要在 `_06` 先做 **goal 模式**。参考 dsh 的 `packages/goal`（一个 package group：
`goal` 服务 + `tool-goal` 模型工具 + `command-goal` 人命令 + `goal-round-driver` 续跑）。

核心诉求三句话：**一个会话一个目标；跨轮次跨重启都记得；模型能自己管、人也能管。**

## 决策

**1) 目标 = 日志的投影，不另存一份。**

每次变更往会话日志追加一条 `goal/change`（携带**变更后的完整快照**），当前目标由
`fold_goal()` 重放出来。于是"跨 turn 持久""跨进程重启""fork 后仍在"三件事**一次都
不用额外做**——它们本来就是"日志是唯一真相"（P1 `_04`）的免费结果。

对照：dsh 用 `sessionProjections` 注册一个 `goal` 投影单元、走严格的 checkpoint
解码。本练习不需要那套通用机制——`fold_goal` 就是一个纯函数，坏日志当场报错。

**2) 一个会话一个目标，且它是"完成条件"不是"待办清单"。**

未完成的目标必须被 pause / complete / clear 之后才能建下一个；**已完成的目标可以
直接替换**（"做完了"和"不想要了"是两件事）。目标 id **不回收**（clear 之后同一个 id
不能再建，防"复活"一个已清掉的目标）。

**3) 版本号 CAS 挡住"拿着旧视图改"。**

每次变更 `revision + 1`；改的时候可带 `expected_revision`，对不上就拒绝并提示
重新读。长对话里模型很容易拿着一小时前的目标视图来改——这条把它拦在写坏数据之前。

**4) 阶段许可表（白名单，不是黑名单）。**

`ALLOWED_TRANSITIONS` 只列出允许的流转；表里没有的一律拒绝。`complete` 是终态
（只能被 clear）；`blocked` 必须带原因（码 + 人话），而 `resume` 兼作解封。

**5) 续跑三道闸门——本阶段最要紧的地方。**

目标 active 时会**自动续跑**，没有护栏就是"一个想不明白的目标烧掉一整天"：

| 闸门 | 作用 |
|---|---|
| 轮次上限（默认 8） | 跑满就标 `blocked`（原因码 `rounds-exhausted`）并写明为什么停 |
| 取消即停 | `cancel` / `stop` 后本轮收尾即止 |
| 只在 active 续 | paused / blocked / complete / 无目标都不续 |

**留痕比静默停止重要**：预算用尽时要写明"跑了 N 轮、上限 M 轮、resume 或提高上限
可继续"——否则用户只看到"它自己不动了"。

**6) 续跑放在 `AgentService.ask`，不在循环里。**

循环只认识"一个 turn"；"要不要再开一个 turn"是**会话级**决策，而会话归
`AgentService` 管。放这一层，两个入口（REPL / 网页）都自动获得续跑，一处都不用改。
续跑的 turn 走完全一样的路径（日志、投影、事件），只有 `user/message` 带
`source="goal-round"`——**目标折叠靠它数轮次**（人插话不算，否则聊两句就把预算耗光）。

**7) 人命令不花模型的钱，且解析只有一份。**

`/goal` 直接操作服务（对齐 dsh 的 `command-goal`）。解析与排版在构件层
（`components/goal/command.py`），网页与 REPL 共用——两个入口各写一遍必然漂移
（一个支持 clear 另一个忘了）。`run_goal_command` **永不抛异常**：打错回用法提示，
而不是把界面搞出 traceback。

**8) `/goal` 的语法：直接写内容就建目标（后补，用户反馈）。**

第一版要求"建目标先打 `new`"，用户真的这么打了 `/goal 写一个飞机大战html`，
拿到的是"不认识子命令"+一长串用法。改成：**先看第一个词是不是子命令，是就执行，
不是就把整行当目标内容**。于是最常用的那条路变成 `/goal <内容>`，子命令留给
"要管它的时候用"（pause/resume/done/clear）。

代价是"子命令打错一个字母"会被静默当成目标内容——所以配了拼写纠错
（`closest_subcommand`）：只对**短英文词**判断，`/goal paus` 提示"想用 pause 吗？"；
中英混排的长句（`暂停一下所有的自动化任务`）不会被误判。

**9) 模型工具三件（`get_goal` / `create_goal` / `update_goal`）。**

`get_goal` 是读（返回紧凑 JSON，含 revision）；`update_goal` 用 `action` 枚举六个
动作。**政策写进工具描述**："只在长程任务时才建目标，日常单轮的事不要建"——
靠模型判断，而不是靠代码猜（代码猜不准"这件事要做几轮"）。

## 备选与排除

1. **把目标存成单独的文件**（如 `goal.json`）。排除：又多一份"真相"，与"日志是
   唯一真相"冲突；而且崩溃恢复、fork、对账全都要为它再写一套。
2. **续跑做成独立的调度器/驱动包**（dsh 是这么分的：`goal-round-driver`）。
   排除（本练习规模）：一个"跑完检查、该续就再调一次 run"的循环闸门语义相同
   （active 才续、有上限、可取消），少一层包。真要并发/排队时再抽。
3. **把目标写进 system prompt 常驻**。排除：那会破坏前缀缓存的稳定前提（`_04`
   的教训），而且每轮都在重发目标——历史里本来就有。
4. **允许同时存在多个目标**。排除：模型会同时开好几条线而每条都半途而废；
   dsh 也是"一个当前目标"，未完成时不许换。

## 后果

- **收益**：目标跨轮次/重启存活且不花额外机制；模型能自管、人能用 `/goal` 管；
  续跑让长程任务真的能自己推进，而三道闸门保证它**一定会停**。
- **实测**：
  - 端到端（离线剧本）：建目标 → 自动续跑 2 轮 → 标记完成后停下，
    `1 人工 + 2 续跑 = 3` 个 turn，`rounds_started = 2`，`goal/change`
    事件序列 `create/active → complete/complete`；
  - 防跑飞：目标永不完成时，跑满 3 轮自动 `blocked`，原因码
    `rounds-exhausted`，`1 + 3 = 4` 个 turn 不多不少；
  - 浏览器实测：命令菜单里 `/compact` 与 `/goal` 并列；`/goal new … --rounds 5`
    → `目标（进行中，revision 1）` → 暂停 → 完成，revision 逐次递增，全程不花
    模型的钱。
- **约束与已知边界**：
  1. 续跑是"跑完一轮再判断"，不是并行调度——一轮很长时暂停要等它跑完；
  2. 目标不调度工作（它只记"要完成什么"）；
  3. `blocked` 之后不会自己好，要显式 resume；
  4. 续跑提示词是固定那一句，背景全在目标与历史里。
- **债务与后续**：todo 清单（PLAN 原定 `_06_Tasks` 的另一半）留待后续阶段；
  `_07_Spill` 是下一个（目标续跑让会话更容易跑长，转存需求更实在）。

## 附：本阶段逼出来的两个真 bug

**① 同名会话有两个 `Session` 对象**（`plugins/sessions.py`）。
`open()` 起初每次新建实例，于是 agent 与 goal 存储各拿一份**内存副本**：一方
append 的事件另一方在自己的 `_events` 列表里永远看不到（磁盘上其实写了），结果
"目标轮次"数成 0、`goal/change` 折不出来。修法是按 session_id 缓存实例——
**日志是唯一真相，真相的句柄也应当唯一**。这是 `_05` 之前没暴露的既有隐患
（那时没有两个消费者同时读同一会话）。

**② 模型工具写死了会话**（`plugins/goal.py`）。
工具面是**全局注册**的（不区分会话），初版把目标写死进 `"default"`，于是在 `g1`
里建的目标跑进了 `default`——`view("g1")` 永远是空的。修法是"现取当前会话"：
`ask` 持锁时把会话名告诉目标服务（与 `_03` 用量账本记 session 的做法一致）。
