# 0034 turn 执行器：并行会话、刷新不掉、可中断

- 日期：2026-10-15
- 阶段：P3_Coding `_05_Compaction`（收尾）
- 状态：已采纳

## 背景

用户问"现在多个会话可以同时并行执行吗"，答案是**不行**——而且是三层串行叠在一起：

```python
# plugins/agent.py（改前）
def ask(self, text, session_id="default"):
    with self._lock:              # ← 一把全局锁，不分会话
        ...
        result = opened.ask(text) # 里面可能跑 30 秒
```

```python
# plugins/webui.py（改前）
with lock:                        # ← HTTP 入口又一把锁
    handle = policy.attach_stream(emit)
    agent.ask(text, session_id=session_id)
```

用户接着提了三条要求：

1. **没必要保留串行**——不同会话应该能同时跑；
2. **刷新页面也要维持对话运行状态，并且能可视化看出来**；
3. **运行中发送新对话应该先选择中断**。

## 决定

### ① turn 跑在后台线程里，HTTP 请求只是"订阅者"

新建 `components/agent/runner.py`。核心是 `TurnRun`（一次 turn 的订阅者名单 + 终帧
+ 完成信号）与 `TurnRunner`（按 session_id 管理）：

    POST /send      → reserve（忙就 409）→ 发响应头 → 挂订阅者 → launch（起线程）
    GET  /turn      → 只订阅（页面刷新后接回正在跑的那个）
    POST /interrupt → 请求取消

**为什么"先发头再起线程"要拆成两步**（`reserve` / `launch`）：HTTP 必须先发
200+chunked 才可能写帧，而"会话忙"又必须回 409（那时还不能发头）。顺序错了会有
真实的竞态：turn 线程先跑、帧发完了订阅者才挂上，客户端一帧都收不到——
内存里的快 turn 尤其明显（回归测试 `test_send_echoes_stream_frames` 当场抓到）。

**订阅者是"随时可来可走"的一组**：帧到达时广播给当前全部订阅者；一个订阅者
写失败（客户端断了）不影响其他订阅者，更不影响 turn 自己跑完。这就是"刷新页面
不掉进度"的实现——**没人看着，turn 照跑**。

不给后来者重放历史帧：每一步都已经写进会话日志，页面刷新后先按日志重建
（`events` 接口本来就含进行中的这一段），再接上实时帧；重放会与日志渲染的那份重复。

### ② 锁的粒度：每条会话一把

`AgentService.ask` 现在只持**这条会话自己的锁**：同会话串行（历史、循环、压缩器
都是那一份对象，交叉写必然乱），**不同会话并行**。全局锁退化成"只护几个 dict
的短临界区"，绝不包住 turn。

观察者也分两层：`open(on_event=)` 保持**替换**语义（终端入口每轮重开时用），
新增 `watch()` 是**追加订阅**（返回退订函数）——并行/刷新时新旧连接会短暂并存，
替换会让先来的悄悄失去推送。

### ③ 推流通道按线程登记（不用 ContextVar）

审批策略原先是一个全局 `_sender` 槽：turn 开始挂上、结束摘掉。串行时代没问题，
**并行之后必然出错**——A 会话在等审批时，B 会话挂上自己的通道覆盖了它，A 的审批帧
就推到了 B 的页面上（或者推丢，等 300 秒超时）。

第一版改成了 ContextVar（"线程局部，被调用的地方无论多深都能拿到"）。**实测失败**：
本项目的阶段目录各持一份同名包、conftest 会驱逐 `sys.modules`——同一个模块可能
被加载成两份，ContextVar 是模块级全局对象，两份副本各有一个，`set` 进去的那份与
`get` 出来的那份不是同一个，永远拿到默认值。（`isinstance` 已经因为这个坑栽过三次。）

改成**按线程 id 登记在服务对象上**（`attach_thread_stream` / `detach_thread_stream`）：
服务对象是运行时单例，与模块身份无关。同时 `TurnRunner` 也不再依赖任何全局——
`ask` 回调直接收到本 run 的 `push`，由调用方决定挂到哪儿（webui 挂给
`agent.watch` 与审批策略两处）。

### ④ 中断是协作式的，且**不粘性**

`cancel()` 只是请求：主循环在 step 边界或流式分块之间看到标记就收尾
（`status="cancelled"`，保留已收到的文本）。正在执行的**工具调用**不会被砍断，
要等它自己返回——这是刻意的（半截命令比等几秒更糟）。

两处必须修的：

- **非流式 provider 调用返回后要补一刀**：取消检查原先只在 step 边界与流式
  分块之间，`complete()` 的整个调用期间按下中断会被忽略，turn 照样以 `done` 收尾。
- **取消不是粘性的**（真 bug）：原先注释写着"之后所有 turn 都取消"。在"中断
  当前 turn 再重新发一条"的用法下，重发的消息会在 0 步处被立刻取消——界面上看是
  "这条会话坏了"。现在取消标记在每个 turn 开始时清零。

### ⑤ 前端：三处可视化 + 一个选择条

- **左栏会话列表**：正在跑的会话带脉冲绿点与"运行中"（数据来自 `/api/sessions`
  的 `running` 字段，由执行器现取，不是从日志猜的）；
- **状态栏**：`第 N 步 · 请求模型…` / `执行工具…`（原有），接回时显示"接回运行中的 turn…"；
- **忙碌选择条**：运行中发消息**不静默吞掉、也不排队**（排队会让人以为发出去了），
  弹三个按钮——`中断并重新发送` / `等它跑完（接着看）` / `取消`。

"中断并重新发送"有两个必须处理的细节：

- **中断可能扑空**（点下去时 turn 刚好跑完）——那不是失败，照样重发；
- **取消是协作式的**，要等正在跑的工具返回，这期间服务端仍回 409。重发时不该把
  用户又弹回选择条（他刚选完），所以带 `retryBusy` 轮询等它让开（最多约 15 秒）。

## 代价与已知边界

- **turn 不再随请求结束而结束**：客户端断开后 turn 继续跑完（这是需求，但意味着
  "用户走了，账单还在涨"）。要真正停掉，得有人按下中断。
- **工具调用不可中断**：一个 30 秒的 shell 要跑完才响应取消。
- **同会话不能排队**：第二条消息要么等、要么中断，没有第三条路（排队被刻意排除）。
- **流式响应不再复用连接**（`Connection: close`）：每次流式请求新建一条 TCP 连接，
  本机场景代价可忽略。

## 实测（全部打在最终代码上）

- **并行**：两条会话同时发消息，A 1.5s / B 1.6s，**重叠 1.5s**（串行需约 3.1s），
  两条都以 `done` 收尾；
- **刷新接回**：跑一半掐断连接 → `running=true`（turn 没停）→ `GET /turn` 接回
  **454 帧**直到 `__done`，日志里 `turn/end` 为 `done`；
- **中断**：长 turn 跑 2 秒后中断 → 终帧 `cancelled`，日志 `turn/end: cancelled`；
- **中断后重发**（完整闭环）：turn 1 `cancelled`（1 步）、turn 2 `done`（6 步）；
- **运行中再发** → HTTP 409 + `busy:true`，界面弹出选择条。

## 顺带修掉的两个真问题

1. **被放弃的流会污染后续请求**（症状极隐晦）：流式响应与普通请求共用 keep-alive
   连接，客户端中止后服务端仍往那条连接写残留帧，**下一次复用它的请求解析歪**——
   实测 `GET /api/sessions` 收到 **501**，界面上的表现是"重发无声无息地没发生"
   （因为那次 fetch 的失败也无人检查）。修法：流式响应一律 `Connection: close`。
   回归测试 `test_abandoning_a_stream_does_not_poison_the_next_request` 钉住
   （去掉修复即失败，已验证）。
2. **`#busy-choice` 元素**同样按"壳的家具"放进 index.html（与 `#banner` 同类），
   静态 id 契约测试自动覆盖。

## 全面测试时又挖出来的三个（同日补修）

用户要求"做一次全面测试看看有没有 bug"之后，用对抗性手法（手工构造时序、把写操作
精确插进临界区、反向验证修复）又找出三处，全部有回归测试且**反向验证过**
（去掉修复 → 测试失败）：

### ① `load()` 的写回截断会吃掉并发 append 的事件（数据丢失）

`JsonlStore.load()` 发现崩溃残尾时会**写回截断**——它**不是纯读**。于是：

    reader: 读到 raw（尾部是半行）→ 判定 good_end
    writer: append 一条新事件（文件变长）      ← 就在这中间
    reader: 写回 raw[:good_end]                ← 刚追加的那条被裁掉

串行时代撞不上；这次改造之后**两件事同时发生**：turn 跑在后台线程持续 append，
而界面每 5 秒轮询 `/api/sessions`（对每条会话调 load）——窗口被反复敲。
修法：`append` 与 `load` 共用一把锁，把"读 → 判定 → 写回"整段罩住。
（`test_load_holds_its_lock_so_a_concurrent_append_survives` 精确把 append 插进
那个窗口，不是靠运气。）

### ② 排队的第二个 turn 会先收到前任的帧（渲染串台）

推流器原先在**拿会话锁之前**就挂上。于是第二个 turn 在门外排队时已经"在听"了——
上一个 turn 的收尾帧（`step_response` / `turn_end` / …）先流到它那里，然后才是
自己的 `turn_start`。客户端照着渲染，凭空多出一条 AI 气泡和一个"turn 完成"行。
修法：`AgentService.ask` 增加 `on_started` 回调，在**拿到锁之后、turn 开始之前**
调用；界面在那里才挂推流器。

### ③ 刷新后待审批卡片回不来（turn 白等 300 秒）

`__approval` 帧只在"等待开始"那一刻推给当时的订阅者。刷新＝换了订阅者，卡片就
永远回不来——而 turn 还在服务端**阻塞等它**（默认 300 秒），到点 fail-closed 拒绝。
用户看到的是"刷新一下，工具就莫名失败了"。后端其实一直提供
`GET /api/approvals`（注释里写着"页面刷新后也能补看到"），**前端从来没调过**。
修法：接回 turn 时补看；并且 `PendingApproval` 带上 `session`——审批可能属于
**另一条**会话（刷新后打开的未必是它），画在当前会话里会让人误以为"这条对话在
等我批准"，批准后也看不到结果。跨会话时改为顶部横幅 +「切过去处理」按钮。

顺带修掉：接回的 turn 跑完后，状态栏停在"第 N 步 · 流式接收中…"（`silent`
把收尾文案一起压掉了）。
