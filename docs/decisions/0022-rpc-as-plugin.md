# 0022 RPC 即插件：JSON-RPC 服务端做成插件（follow = 重放 + 订阅）

- 日期：2026-10-13
- 阶段：P3_Coding（基础包增补）
- 状态：已采纳

## 背景

决策 0021 把界面做成了插件，但明确记着一条边界："事件流只推给发起 turn 的
那个客户端（多客户端广播属于 RPC / 事件流跟随的题目）"，以及一条级联问题：
"换底层插件会连带重启界面——需要稳定门面时应走 RPC 服务"。

P2 有完整的服务化（`_10` stdio JSON-RPC、`_11` `session.follow` 事件流跟随 +
断线补齐），但它在 P2 的架构里是"手工起的服务"（`serve.py` 组装一切）。
P3 要把它重做成**插件**：服务端自己就是一个声明依赖的插件，装载即起、
卸载即停、多客户端共享同一会话。

## 决策

**1) 新增 `plugins/rpc.py`（第九个标准插件）+ `components/rpc/` 构件**
（协议帧 + 传输）。方法与 P2 一致：`initialize`（握手 + 能力清单）、
`session.prompt`（跑 turn）、`session.follow`（事件流跟随）。

**2) `follow = 重放 + 订阅`，且推送粒度是"每条会话事件"**：

- **事件源**：`sessions` 插件产出的会话升级为 `ObservableSession`——每次
  `append` 成功后立刻 `ctx.emit("session/event", ...)`。这是唯一的新机制
  （十行代码）；**真相仍在日志里**，事件只是"日志长了"的实时通知。
- **重放**：`follow` 从日志取 `seq > from_seq` 的既有事件逐条推；
- **订阅**：登记 `(session, last_seq, sender)`；此后每条新事件立即推送；
- **无缝衔接**：重放与登记在**同一把锁**内完成——重放结束的 `last_seq` 就是
  订阅起点，不重不漏。断线补齐由客户端带 `from_seq` 重连触发：**补缺靠重放
  日志，不靠任何缓存**（事件溯源在服务化上的回报，与 P2 同一条纪律）。

**3) 两种传输、一对语义**：

    rpc_plugin()                 提供 `rpc` 服务（stdio 由入口驱动；无端口）
    rpc_plugin(listen=8765)      装载即起 TCP（默认只听本机），卸载即停（端口释放）

stdio 模式的**协议线纪律**由入口落实：`chat.py --rpc` 把 banner/台账全部改走
stderr（`show_ledger(stream=...)`），stdout 只出帧——这是 P2 `_10` 踩过的坑，
现在有一条真实子进程的回归测试钉住（`test_p3_rpc_entry.py`）。

**4) 线程安全下沉到 agent 服务**：`AgentService.open/ask` 用可重入锁串行化
（会话缓存、观察者注册、剧本 provider 都不是线程安全的）。webui 与 rpc 可能
从不同线程同时发起 turn；各入口自己的锁只管本层语义（webui 的标签页绑定），
**底层保障只有一处**（agent 的锁），避免"每个入口各写一套"的重复与遗漏。

**5) 订阅台账归插件显式撤销**：订阅列表是 ctx 管不到的"外部状态"（与
`ToolRegistry` 同理），插件在 disposer 里 `service.close()` 清空；连接断开则由
`LineTransport.serve_forever` 的 finally 调 `drop_sender(channel)` 注销该连接
的全部订阅——**订阅不泄漏**（两条路径都有测试）。

## 备选与排除理由

1. **复用 P2 的 `serve.py`（把装配代码搬过来）**。排除：那正是要改的形态——
   服务不该自己组装 harness；它应该是插件，`ctx.require("agent")` 即可。
2. **推送用"轮询日志"（follow 只登记，不实时推）**。排除：长 turn 进行中看不到
   事件流生长，且把"何时重读"的责任推给客户端。行内推送（每条 append 即推）
   才是 P2 `_11` 的语义。
3. **在 write 路径做广播（Session.append 直接回调订阅者）**。排除：让会话构件
   认识"订阅者"会把服务化泄漏进日志层。中间隔一层内核事件（`session/event`）
   保住了分层——订阅者只认事件，会话只管写。
4. **每个连接一个 RpcService 实例**。排除：那样多客户端不共享会话缓存（同一
   会话在两个客户端上会互相看不见），且 subscribe 的 sender 归属变复杂。
   单例 service + 每连接 Channel 才是"多客户端共享同一会话"的正确形状。

## 后果

- **收益**：P3 补齐了"稳定门面"——界面可以直接换成 RPC 客户端而底层不动；
  TCP 多客户端共享会话、跨连接推送、断线 `from_seq` 补齐全部有测试；
  stdio 协议线纯净性有真实子进程回归测试。
- **约束与已知边界**：
  1. **无鉴权、默认只绑本机**（与 webui 同一取舍）；
  2. **无版本协商**：`initialize` 只报版本，不做兼容分支；
  3. **推送是"尽力而为"**：Channel 写失败即静默关闭（不炸正在跑 turn 的线程），
     断线期间的事件靠重连重放补齐——这是设计，不是缺陷；
  4. **turn 串行**：agent 的锁让"两个客户端同时提问"变成先后执行（不并发）。
     对单机小 harness 是正确的取舍；真并发属于后续（多会话并行）。
- **债务与后续**：
  1. **没有随附 attach 客户端**（P2 有 `attach.py`：流式渲染 + 自动重连 + 补齐）。
     在 P3 里它是独立小工具，可基于 `components/rpc` 直接写；
  2. **webui 与 rpc 各自一套"会话/事件读取"**（webui 的 `_sessions_overview` /
     `_session_detail` 与 rpc 的重放逻辑有重叠），可提取为共享只读服务；
  3. `session.follow` 的订阅在**同一会话多订阅者**时是逐条推送 N 次（无批量合并）。
