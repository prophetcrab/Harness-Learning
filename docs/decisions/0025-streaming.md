# 0025 流式输出：可选能力接缝 + 纯函数聚合 + 瞬态事件

- 日期：2026-10-14
- 阶段：P3_Coding `_02_Streaming`（P3 第二个阶段）
- 状态：已采纳

## 背景

到 `_01` 为止，模型调用都是"一次性返回"：`complete()` 阻塞到整条回复生成完毕。
界面上表现为——发问后长时间静止，然后整段文字突然出现。真实产品（以及 dsh）都是
逐字流出的，用户能看到进展，长回答也不至于"卡住"。

技术上要回答三个问题：

1. **怎么加**？dsh 的 `LlmAdapter.stream()` 是主接口；我们的 `complete()` 已有一批
   实现与测试（FakeLLM、RepeatingLLM、DeepSeek、每步渲染包装、llm 插件代理）。
   直接把协议改成流式会打断全部既有代码。
2. **聚合放哪**？厂商给的是 SSE 帧流（文本片段 + 工具调用的 JSON 字符串碎片），
   而循环需要的是**一条完整的 LLMResponse**（消息、tool_calls、finish_reason）。
3. **取消怎么做**？用户点了取消，正在生成的流要停，但**已经收到的部分不该丢**。

## 决策

**1) 加"可选协议"，不改主协议。**

    LLMProvider            complete(请求) -> 响应            ← 既有，不动
    StreamingLLMProvider   stream(请求) -> Iterator[增量]     ← 新增（`_02`）

消费方（主循环）用 `hasattr(provider, "stream")` 探测：有就走流式，没有就退回
`complete()`。同一份 `FakeLLM` 剧本既能被 `complete()` 聚合、也能被 `stream()`
逐片播放——**"流式与非流式结果一致"因此成为可断言的性质**，而不是靠人工核对。

代价是"能力探测"成为契约的一部分，于是引出一条纪律：**包装器必须诚实**。
实测踩到过——每步渲染包装和 llm 插件代理最初"总是暴露 `stream`、调用时才报错"，
导致只有 `complete()` 的 provider 被当流式调用直接炸。现在两个包装器都改成
按内层能力决定是否暴露 `stream`（内层不支持就没有这个属性）。

**2) 聚合是纯函数，落在构件层。**

    StreamChunk                          中立增量（文本片段 / 工具调用分片 / 末帧）
    aggregate_chunks(chunks) -> LLMResponse    纯函数，唯一的语义出口

规则：文本顺序拼接；工具调用按 `tool_index` 分组，各自的 id/name/参数片段分别累积，
**参数拼完才 `json.loads`**；`finish_reason` 取最后一个非空值。拼完不合法（不是
JSON、缺工具名）就 fail loud——宁可让这一步炸，也不把半个工具调用塞给工具层。

厂商方言（SSE 的 `delta`、分片 `tool_calls`）留在 provider 里（`chunk_from_delta`），
与既有的 `message_to_wire` / `response_from_api` 同一层——**方言边界不搬家**。

**3) 增量是"过程"，不进会话日志。**

`step_delta`（每次增量）与 `stream_cancelled`（中途取消）是**瞬态事件**：
只发给观察者（界面、RPC 订阅者），`SessionRecorder` 直接忽略它们。日志里记录的
仍然是聚合后的 `assistant/message`。

理由：日志是**事实**（模型到底回了什么），增量是**过程**（它是怎么吐出来的）。
把增量写进日志会让体积爆炸（一条回复几十行）、投影变复杂、重放不再同构，
而换不来任何"可回溯"的收益——聚合结果本身就是完整事实。

**4) 取消保留已收部分，且不执行半截工具调用。**

`cancel()` 与 `should_stop` 回调在**增量之间**生效（流式中没有别的检查点）。
取消后：关闭上游生成器（provider 的 `finally` 收尾，DeepSeek 侧会关掉 SSE 响应）、
用已收到的片段聚合、**丢弃半截的 tool_calls**（参数没拼完就执行是危险的）、
turn 以结构化 `cancelled` 收尾并把部分文本带回。

**5) 传输层：真流式必须 HTTP/1.1 + chunked。**

浏览器侧要"逐字"看到效果，服务端就得**边生成边 flush**。实测踩到：`http.server`
默认 HTTP/1.0，响应既没有 Content-Length 也没有 chunked，客户端只能等连接关闭才
认账——"逐字到达"退化成"一次全到"。修法：`protocol_version = "HTTP/1.1"` +
显式 `Transfer-Encoding: chunked`（手动分帧）+ 每帧 flush + 收尾写零长度块
（放在 `finally` 里，异常路径也要收口，否则客户端一直等）。

## 备选与排除理由

1. **把 `complete()` 直接改成流式并让实现自己聚合**。排除：打断全部既有实现与测试；
   而且"聚合"会散落在每个 provider 里（五份实现 = 五处重复的拼接逻辑）。
2. **聚合放在循环里**。排除：循环就多了一份"怎么拼"的知识，而它本该只关心
   "一次调用得到一条响应"。聚合是纯函数、放构件层，谁都可用、可单独测。
3. **增量也写进会话日志**。排除：见决策 3。日志体积、投影复杂度、同构性都是代价，
   收益为零（聚合结果已完整）。
4. **取消时直接丢弃整轮输出**。排除：用户看到一半的内容突然消失，体验更糟；
   保留部分文本 + 明确标注"已取消"更诚实。

## 后果

- **收益**：回复逐段到达（真实 API 实测 101 个增量 / 0.52s 跨度，`Transfer-Encoding:
  chunked`）；流式与非流式在同一份剧本下结果一致（有测试）；取消保留已收部分且
  不执行半截工具调用；日志体积与投影逻辑完全不受影响。
- **约束与已知边界**：
  1. **首片延迟 = 模型思考时间**（实测 ~11 秒），流式不能让"等待"消失，只是让
     等待之后的吐字可见；
  2. **能力探测是隐式契约**：包装器必须诚实暴露/隐藏 `stream`（两处已有注释与测试）；
  3. **取消粒度是"增量之间"**，不是"字节之间"——同步生成器无法更细；
  4. 流式路径的 `usage` 目前**未聚合**（OpenAI 兼容协议在末帧带 usage，
     `StreamChunk` 暂未承载）——留给 `_03_Usage_Budget`。
- **债务与后续**：
  1. `_03` 需要把流式末帧的 usage 接进 `aggregate_chunks`；
  2. 界面未做"打字机节奏"（增量到达即渲染，真实速度可能很快，视觉上偏"闪"）；
  3. RPC `session.follow` 已能收到 `session/event`，但增量（`step_delta`）走的是
     主循环事件流，未接进 RPC 的推送——需要时再补（属平台档）。
