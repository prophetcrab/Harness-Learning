# 0014 配置可见：字段级来源台账，错误带层与位置

- 日期：2026-10-09
- 阶段：P2_Coding/_09_Dump_Config（学习计划 M6 第三步，**M6 收官**）
- 状态：已采纳

## 背景

`_08` 把装配变成了配置数据、立了四层叠加，但留下两笔债（都记在 0013 的"后果"里）：

1. **`--dump-config` 看不见来源**：打印的树只有最终值——"这个 shell_timeout 是谁定的"
   还要人工翻多层文件比对。分层的好处是每层只管一行，代价就是"值散在多处"；
   没有来源标注，这个代价就由使用者全额承担。
2. **配置错误定位不够**：patch 指向不存在的行会报错（`_08` 已做），但：
   - 错误消息不带"哪一层、第几条"；
   - `config` 是自由字典——`shell_timeou`（拼错）静默失效，最迷惑的一类问题；
   - 拼错的 id / 插件名只有"现有值列表"，没有"你是不是想…"。

本阶段的目标（README 两条验收）：dump 可读且**显示来源层**；配错启动即报错并
**指出位置**。

## 决策

**1) 来源追踪做在"数据流"上，粒度到字段**（`ConfigTree.sources`）：
台账是 `行 id → {name/config/disabled: 层标签}`。三个写入点：
`load_tree` 给所有字段打文件名的初始标签；`apply_patch` **只为它实际改过的字段**
更新标签（"给了就换、没给沿用"——沿用字段的来源必须保持旧值，否则 dump 会撒谎）；
`load_profile` 给 CLI 补丁编号（`CLI#1 xxx.yaml`，多层可辨先后）。

**为什么是字段级而不是行级**：patch 的粒度是字段（可以只换 name 不动 config）。
行级标记在"name 来自 CLI、config 还来自 base"时会显示成一句含糊的"来自某一层"，
用户还是要翻文件；字段级才是"每项可读"。

**2) 台账挂在 ConfigTree 上、所有复制路径都要带上**：`copy()` 深拷贝 sources，
`apply_patch` 在副本上更新——输入树（以及它代表的下层）永不被改动。纯数据构造
（`from_dicts`）没有台账，渲染时给 `（未知来源）` 占位而不是猜。

**3) 渲染单独成层**（`config/dump.py`）：`render_tree(tree) -> str`（返回字符串、
不打印——可测、可复用）；`source_summary` 给按层的第二视角。格式刻意平实
（`字段 = 值 ← 层`），便于 grep 与快照测试。

**4) 错误定位三件套**（层名 + 条目序号 + 拼写建议）：
- `Patch` 新增 `label`（层标签，默认取文件名；CLI 层带序号）；
  `apply_patch` 的报错形如 `dev.yaml 第 1 条 patch：行 id 'toolbx' 不存在…`；
- 拼写建议用 `difflib.get_close_matches`（id、插件名、config 键三处）；
- **`PLUGIN_CONFIG_KEYS` 白名单**（每插件声明它接受哪些 config 键）：
  未知键 fail loud 并列出可用的——`.config` 从"自由字典"变成"有契约的字典"，
  参数拼错不再静默失效。这收掉了 0013 记下的第二笔债。
- 工厂里的类型错（`shell_timeout: "很快"`）由 `build_plugins_from_tree` 包装成
  `行 'toolbox'（toolbox）的参数有问题：…`——错误定位不漏"值不对"这一类。

**5) 校验发生在副作用之前，分工不重叠**：结构问题（未知行/重复 insert/未知键）
在读文件与 patch 应用时报；语义问题（未知插件名/未知参数键/类型错）在
`build_plugins_from_tree`（构造阶段）报；装载问题（槽位冲突）由 kernel 回卷。
用户看到的每条错误都知道"哪一层、哪一行、第几条"。

## 备选与排除理由

1. **dump 不带来源（只打印最终值）**。排除：那等于把 `_08` 分层的可读性收益
   丢掉一半；验收第一条就要求"显示来源层"。
2. **行级来源标记（粒度到行）**。排除见决策 1：字段级才回答"这一项是谁定的"，
   且成本极低（一个嵌套 dict）。
3. **来源信息写进 ConfigRow 的每个字段旁边**（改行结构）。排除：行是"值"的载体，
   来源是"流的痕迹"；混在一起会让行的相等性判断、序列化、快照测试全变复杂。
   单独一张台账（sources）职责清晰。
4. **`config` 继续做自由字典（不校验键）**。排除：`shell_timeou` 这类拼错
   在运行时表现为"配了个没用的值、行为还是默认"——排查成本极高的静默失效；
   fail loud 是铁律 #8 最典型的适用场景。代价是新增插件要在白名单里登记，
   用"工厂与白名单键集合必须相等"的测试钉住（忘登记会被测试拦下）。
5. **拼写建议用编辑距离自实现**。排除：标准库 `difflib.get_close_matches` 一行
   到位，无理由自研。

## 后果

- 约束：`apply_patch` 现在承担"更新台账"的职责（只对该 patch 实际改过的字段）；
  `load_tree` 是台账的初始化点——绕过加载器（纯 `from_dicts`）构造的树在 dump 里
  显示"（未知来源）"，这是刻意的诚实降级。新增插件必须在 `PLUGIN_CONFIG_KEYS`
  登记（有测试强制）。
- 收益：**"每项来源"与"错误位置"两条验收都可执行**——dump 里 `← dev.yaml /
  ← CLI#1 pin.yaml` 逐项可读（真实 API 验证过：一层补丁后 llm 行来源变成
  `CLI#1 pin.yaml`、其余行原样）；七类配置错误全部 fail loud 且带定位/建议
  （demo 0b 逐条演示）。53 个用例（22 基线 + 31 新增），全项目 679 用例全绿；
  跨 `_01`–`_09` 同进程 541 用例无串味。**M6 收官**。
- 债务与后续：
  1. **`--dump-config` 仍是阶段入口（chat.py）的功能**，不在冻结的 `harness/cli.py`
     里（`python -m harness --profile dev dump-config` 这条计划里的统一命令尚未接线；
     归因于 P2 的"harness 冻结"约定与阶段式工作区，待未来做独立 CLI 时收编）。
  2. **来源只到"层"不到"条目"**：dump 显示 `CLI#1 pin.yaml`，不显示"该文件第 3 条"；
     出错误定位时会到条目级，两者粒度不同是有意的（dump 面向阅读，错误面向修）。
  3. **Windows 子进程输出编码**（0012 的债务）仍未处理，与本阶段无关但继续累积。
