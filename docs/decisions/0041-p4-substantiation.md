# 0041 P4 定调：实质化 —— 自有最小插件底座 + 三类插件 + 一个项目

- 日期：2026-10-16
- 阶段：P4_Coding（目标已定，未开工）
- 状态：已采纳

## 背景

P3 收官时留下两个未了的账：

1. 三处"还不够插件化"的差距（主循环不是插件 / 工具管线不属 tools / 管线策略层
   没有插座）——它们都指向同一件事：**组合与策略还长在底座里**；
2. P3 是**学习形态**：每个机制一份阶段目录副本，组合写在 `boot.py` 的参数里。
   它证明的是"机制能长出来"，不是"它能变成一个产品"。

用户给定的 P4 方向（原话）：

> 将整个项目实质化：首先做一个基础的插件管理的底座（类似 cordis，不需要 cordis
> 的额外功能，只需要辅助完成插件管理），然后分类插件类型：基础插件（整个 harness
> 所依赖的最小插件，包含 LLM 配置，AgentLoop 等），应用化插件：通过选配的外层
> 包装配合基础插件形成不同的产品，能力插件：为……
> 然后直接在 P4 的一个项目里逐步完善整个 harness 形成一个可用产品。

## 决定

**一、底座自研、边界写死**：做一个只服务"插件管理"的最小内核（服务槽位、事件、
effect 回卷、依赖声明、装卸停启、台账、装配单、插件配置）。**明确不要** cordis 的
fork / 隔离作用域、HMR、配置 schema 框架、反射式 DI、工具集——理由：本项目的目标
是**理解**插件系统的骨架，不是复刻一个工业级框架；要多一样，先能说出它解决了哪个
真实问题。

**二、插件分三类**（`base` / `application` / `capability`）：

| 类别 | 判据 |
|---|---|
| 基础插件 | 卸了它，**任何产品**的 harness 都残缺（含 LLM 配置、AgentLoop、日志、工具面、提示词） |
| 应用化插件 | 换掉它，**产品形态变了**（web / cli / sdk / headless），内核不动 |
| 能力插件 | 装卸它，**产品形态不变**，只是多 / 少一件事（工具、压缩、计量、审批、管理） |

配套两条：分类（是什么）与"能不能卸"（装配方策略）分开，沿承决策 0035；
**每个产品至少要有一个应用化插件**——这条做成装配期检查（fail loud），
不靠文档提醒。P3 的 `other` 取消（演示插件归入能力插件）。

**三、一个项目、不再分阶段副本**：P4 目录本身就是那个产品；里程碑（底座 →
基础插件 → 能力插件 → 应用化 → 可用产品）只表示内部进度。验收是
"三形态可用 + 狗粮跑通 + 门禁绿"，不是"阶段 N 的四件套"。

**四、闭上三处差距不是额外任务**：它们本来就是"基础插件"定义的一部分——
AgentLoop 被点名要进基础插件，那就必须能独立装卸；管线要能挂策略，
那 `tools` 就得同时拥有管线与中间件插座。

## 代价（如实记下）

- **自研底座会重踩 cordis 踩过的坑**（作用域、依赖环、卸载顺序）。取舍是：
  这些坑是学习目标的一部分，而 cordis 的完整实现会让"看懂"这件事本身变难；
- **不再有"上一阶段完成态可复制"这个支点**：P4 是在一个活的目录里改动，
  每步都要门禁绿——比 P3 的"复制起步"更容易把东西改坏（这也是 P3 那三处
  差距能一直躺着的原因：阶段副本天然容忍"下个阶段再说"）；
- **"可用产品"是主观词**：所以把它落成可核的三条（三形态起得来、狗粮任务
  走完、门禁绿），而不是"感觉能用了"。

## 备选方案与否决理由

**A. 直接用 cordis（P4 变成"用 cordis 重写 P3"）。**
P7 的课题（回到 dsh 写插件）就是它；在 P4 提前用，会把"自己实现一个插件内核"
这个学习目标让出去，而且 P3 的三处差距（循环插件化 / 策略插座）在 cordis 上
同样要自己动手做——只是换了个地方做。

**B. 继续 P3 的阶段副本模式（`_07` 循环插件化、`_08` …）。**
副本模式适合"单机制对比学习"，不适合"补成一个产品"：产品里这三件事必须同时
成立（循环是插件 + 管线有插座 + 组合是数据），分三份副本做反而看不到它们
如何互相牵制。

**C. 先定垂类再补能力（P3 PLAN 的旧主张）。**
垂类决定"哪些深插件值得做"（P5 的课题），但 P4 要的这批是**通用能力**
（工具 / 压缩 / 计量 / 审批 / 管理），任何垂类都要；而且 P4 的验收是产品形态，
与垂类无关。垂类仍留给 P5。
