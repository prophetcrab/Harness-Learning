# 0030 任务清单：整表快照进日志，模型不带序号、人带序号

- 日期：2026-10-14
- 阶段：P3_Coding `_06_Tasks`（P3 第六个阶段）
- 状态：已采纳

## 背景

PLAN 的 `_06` 原定"**todo 工具（增/列/完成）+ goal 状态进日志**"。开工时先做了
goal（另一个文件、另一个阶段），用户随后要求撤回 goal、回到 PLAN 原本的计划。

撤的时候想清楚了一件事：**这两样东西的性质不同，不该挤在一个阶段里**。

    todo   回答"接下来做哪几步" —— **状态**：清单进日志，投影派生
    goal   回答"做完是什么样"   —— **控制流**：要改循环的终止状态（等批准 / 自动续跑）

PLAN 的纪律是"一个阶段一个机制"；把一个状态机制和一个控制流机制绑在一起，
出问题时分不清是哪边错，验收也会糊。所以本阶段**只做 todo**，goal 留待需要时
另开阶段（PLAN 的表格里已注明这次拆分的理由）。

## 决策

**1) 整表替换，不是增量更新。**

每次 `todo_write` 携带**完整的新列表**，直接替换旧的（对齐 dsh 的 `todo_write`）。
三个后果，全是好的：

- **条目不需要 id**：整表之下没有稳定身份可言；
- **折叠只有一条规则**：最后一条 `todo/write` 赢（last-write-wins），不用逐条重放；
- **模型不必有索引意识**：增量最容易错的地方就是"我以为第 2 条是跑测试"。

代价是每次多花一点 token（一张十几条的清单）。值——索引错位的代价是改错条目。

**2) 三条约束，写入前拒绝；不写半张表。**

| 约束 | 理由 |
|---|---|
| 内容非空、不重复 | 空条目 / 同一条出现两次 = 模型没想清楚 |
| **同时最多一条 `in_progress`** | 一次做一件事。多条并行是人的习惯，不是 agent 该学的 |
| 最多 50 条 | 防模型把整个需求文档抄进来 |

校验集中在 `domain.normalize`（唯一入口：服务层、模型工具、人命令都走它）。
不满足就**不写**——坏事件会毒死以后每一次重放（`_06` goal 原型上吃过这个教训）。
`fold_todos` 里还有第二道同样的校验：写入期防错，重放期防坏。

**3) 模型不带序号，人带序号。**

- 模型侧只有一个 `todo_write`，必须发整表——它**不该维护索引**（见决策 1）。
- 人命令 `/todo` **支持序号**（`/todo done 2`）：清单短，人一眼看得到第几条，
  敲数字比抄一整句快。序号只是人机接口的便利，不进入日志语义。

**4) 清单不驱动续跑。**

这是与 goal 类机制的分界线。如果清单也能触发自动续跑，模型随手列个十步计划
就等于给自己签了一张十轮的支票。持续推进该由"完成条件"那类机制负责
（`goal` 的自动续跑；本阶段不做）。测试里专门钉住了这条（写清单不产生额外轮次）。

**5) `/todo` 靠"第一个词是不是子命令"分流。**

```
/todo 读需求         → 第一个词不是子命令 → 整行当新条目（最常用，不用打 add）
/todo done 2         → 是子命令 → 执行勾选
/todo                → 不带参数 → 看清单（带序号）
```

与 `/goal` 的语法一致（那里也是"想说内容就直接说"）。这套分流在
`components/todo/command.py`，网页与 REPL 共用一份——两个入口各写一遍解析
必然漂移。

## 备选与排除

1. **增量更新（`add_todo` / `complete_todo` 分开）**。排除：模型要维护索引意识，
   错位改错条目；而且折叠要逐条重放并处理"第 3 条被删了"这类对不上号的情况。
2. **给条目加 id**。排除：整表替换之下 id 没有用处，加了就是"两套身份要同步"。
3. **允许并行多条 `in_progress`**。排除（本练习）：串行是一句值得写进约束的纪律；
   dsh 把它做成配置项，我们取严的那一档。
4. **清单也参与自动续跑**。排除：见决策 4，会让清单变成"十轮支票"。
5. **界面做成弹窗**。排除：清单是"模型自己拆的步骤"，用户该随时看得见——
   做成右上角**常驻面板**（`#todo-box`），模型改了立刻反映。

## 后果

- **收益**：清单跨 turn / 重启 / fork 存活且不花额外机制（日志是唯一真相的又一次
  兑现）；模型能规划并显示进度；人能用 `/todo` 直接管而不花模型的钱；
  界面右上角常驻面板随时可见。
- **实测**：模型在 `g1` 里调 `todo_write` 写入三条（一条 completed、一条
  in_progress、一条 pending）→ 清单落在 `g1` 的日志里（不是 default）→
  重启装配后逐字相同 → 能继续改；写清单不产生额外 turn。
- **约束与已知边界**：
  1. 清单是"模型的工作记忆"，不是硬性计划——它可能不按它执行，也可能中途重写
     整张表；约束只保证格式对、单条在做；
  2. 不做依赖关系 / 优先级（dsh 的 todo 也只有 content + status 两样）；
  3. 超长清单只靠 50 条上限兜，不做分页。
- **债务与后续**：`_07_Spill`（大输出转存）是下一个。goal 那类"完成条件 + 自动
  续跑"若需要，另开阶段（PLAN 里已注明拆分理由）。

## 附：本阶段保留的两个 bug 修复

做 goal 原型时挖出两个真 bug，goal 撤销后修复保留了下来（todo 同样会踩）：

**① 同名会话有两个 `Session` 对象**（`plugins/sessions.py`）。
`open()` 起初每次新建实例，于是 agent 与清单存储各拿一份**内存副本**：一方
append 的事件另一方在内存里永远看不到（磁盘上其实写了），清单于是读不出来。
修法：按 session_id 缓存实例——**日志是唯一真相，真相的句柄也应当唯一**。

**② `#banner` 元素从来不存在**（`webui/index.html`）。
`showBanner` 被四处调用（压缩失败、日志修复提示、`/todo` 结果……）却从无此元素，
那些路径一执行就抛错。`/todo` 用 banner 显示结果才把它暴露出来。
