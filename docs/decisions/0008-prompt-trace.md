# 0008 装配单：把"怎么拼出来的"记进日志，重建校验有牙齿

- 日期：2026-10-08
- 阶段：P2_Coding/_03_Prompt_Trace（学习计划 M4 第三步）
- 状态：已采纳

## 背景

`_01` 立了 section 结构、`_02` 让提示词每 step 动态渲染，但**过程没有留下痕迹**：
`session/start` 与 `system/message` 里只有一段最终文本，事后无法回答三个问题：

1. 这一节是谁贡献的（内置？哪个作用域？）；
2. 当时 `{{cwd}}` / `{{time}}` 取什么值；
3. 更要命的——"模型当时看到的提示词能被重建"这句话，拿什么来**验证**？

M4 的验收里写着两条："`--dump-prompt` 打印装配过程与来源"、"渲染出的提示词必须能由
「日志 + 装配器」重建"。前者要展示信息，后者要一条**可被反复检验的不变量**。`_02` 结束时
`source` 字段还只是打标签、`parts()` 还没人消费；本阶段把它们变成产品。

## 决策

**1) 引入装配单（PromptTrace）作为新的持久化词汇**（`prompt/trace.py`）：
每次渲染产出一份结构化记录——每节的 name / source / title / **模板** / 渲染文本 /
引用变量，整份的变量取值 / 分隔符 / 最终文本。关键取舍：记**模板**而不只是渲染结果——
模板是"这一节引用了什么"的静态事实，变量取值是"这一次渲染"的动态事实，两者分开，
重放才能复现。

**2) 装配单随事件进日志，而不是另开事件类型**：`session/start` 与 `system/message`
增加 `prompt_trace` 字段，文本仍是主字段。理由：装配单是"这份文本的来源说明"，
不是独立事实；绑在同一条事件里，遮蔽链（最近一次生效）天然把两者绑在一起，
`_02` 的投影代码一行不用改就能继续工作（向后兼容：读不到 `prompt_trace` 时行为不变）。

**3) 重建是"从记录出发的再装配"**（`rebuild_text`）：新建一个空注册表，把记录里的模板
逐节注册回去（来源也如实填回），再用与渲染时相同的装配器（同一分隔符、同一插值函数）
拼一遍。**刻意不依赖进程里的原注册表/作用域**——`test_rebuild_does_not_need_original_registry`
里把原结构 `del` 掉后照样重建成功，证明记录自足。

**4) 让检验有牙齿**：重建结果与记录文本逐字节比对。改掉记录文本、改掉某一节模板、
抹掉一个变量，都必须被抓住——前者/中者"重建 ≠ 记录"，后者 fail loud。如果重建偷偷
"照抄 text 字段"，这层校验就是摆设；所以重建只信模板 + 变量，`text` 字段仅作比对对象
（`test_tampered_text_is_detected` 钉死这一点）。

**5) 追溯读取与展示**：`context.latest_prompt_trace(events)` 取当前生效装配单
（与 `effective_system_prompt` 同一条遮蔽链）；`chat.py --dump-prompt` 逐节展示
来源/引用变量/模板与渲染对比，末尾打印重建校验结论；会话内 `/prompt` 看的是**日志里**
的装配单——追溯"当时"而不是重新渲染"现在"（两者在时间变量上必然不同）。

## 备选与排除理由

1. **新建 `prompt/trace` 事件类型**。排除：装配单与它描述的文本是同一件事实的两面，
   分开存会引入"文本事件与装配单事件谁跟谁配对"的同步问题，遮蔽链也要写两遍；
   字段挂在既有事件上零成本且天然配对。dsh 的 message `source` 字段（来源随消息走）
   也是同一思路。
2. **只记渲染后的各节文本，不记模板**。排除：模板是重建的"原料"，只记结果等于把
   渲染器复刻一遍的负担留给将来；记模板 + 变量，重建就是确定性的再装配。
   顺带：dump-prompt 里"模板 vs 渲染"并排展示，正好回答"这节在哪儿用了变量"。
3. **重建时复用进程里的原装配器/注册表**。排除：那样"重建"沦为自证——原结构若已
   随进程消失（这就是回溯场景本身），重建能力根本不存在；且无法检验记录是否自足。
4. **重建"宽松模式"（缺变量就用空串顶替）**。排除：静默降级会造出一份"看起来对"
   的假文本，追溯的价值恰恰在于不确定时报错。fail loud 与 `_02` 插值的纪律一致。
5. **装配单只打日志不校验**。排除：不校验就没有"重建断言"这个验收；篡改检测
   （文本/模板被动过）是让它有牙齿的最小手段。

## 后果

- 约束：`prompt/` 仍是纯逻辑包（trace.py 只依赖 Section/注册表/插值，不碰 harness）；
  装配单 schema 一旦进日志就有兼容包袱——`from_dict` 对缺字段取保守默认，将来扩展
  新字段时旧日志仍可读。
- 收益：`--dump-prompt` 可读且含完整来源；"日志 + 装配器 == 当时提示词"成为测试与
  demo 都在跑的不变量（含"篡改检测"与"原结构已丢弃"两条硬用例）；`source` 字段
  从 `_01` 起的铺垫开始真正被消费。49 个用例（22 基线 + 27 新增），全项目 417 用例全绿。
- 债务与后续：
  1. **装配单体积**：模板 + 渲染文本逐节双份，长提示词会让事件变大（每条
     `system/message` 都带一份）。当前提示词很小，不构成问题；若提示词规模化，
     可考虑"模板池 + 引用"或压缩（dsh 对日志整体用 Zstandard）。
  2. **重建不校验 source/title**：它们不参与文本，篡改它们不会被"文本比对"抓住；
     若将来来源信息被程序消费（而非只读展示），需要给它们加校验或哈希。
  3. **M4 收官**：`--dump-prompt` 目前是本阶段入口（chat.py）的开关；等 M6 的
     profile/CLI 组装落地后，统一入口 `python -m harness run --dump-prompt`
     （计划里的招牌命令）再接线，避免现在就去改冻结的 `harness/cli.py`。
