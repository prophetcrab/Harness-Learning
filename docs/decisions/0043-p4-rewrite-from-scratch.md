# 0043 P4 全部重写：不搬 P3 代码，逐个小步写

- 日期：2026-10-16
- 阶段：P4_Coding（基座开工）
- 状态：已采纳

## 背景

P4 PLAN 第 5 节原本建议"先搬后收"：把 P3 的 `kernel/`、`components/`、能力插件
整段搬过来再收敛。用户在基座设计的三轮讨论后决定（2026-10-16，原话）：

> P4 不要搬了，全部重新写，我们一点一点的来写，不要着急。

## 决策

**一、P4 不搬 P3 任何代码，每一行从零写。** P3 只作两类参考：

- **语义对照**：同一个机制 P3 是怎么实现的——动手前读一遍，确认没漏掉语义
  （例：optional 依赖"缺了照常激活、来了不重装"；退位顺序"深的先退"）；
- **教训清单**：P3 决策记录里的坑——0031（声明纪律）、0035（角色由装配方定）、
  0038（源码即插件的三处实测教训）、0039（端口 / 面板 / 日志）——写相关机制前先读。

**二、小步节奏**：M1 拆成 8 步（见 PLAN 的「拆步」表），每步"先写验收（测试）→
实现 → 绿了才下一步"；每步单独评审、单独回退。不追求一个里程碑一次做完。

## 备选与排除理由

**A. 先搬后收（PLAN 原案）。** 三条否决理由：

1. **学习目标是"写出来才算理解"**：搬代码把最要学的环节让出去了——P4 的性质是
   实质化（0041），亲手把机制长出来本身就是目的；
2. **P3 代码带着 P3 时期的结构**（组合写在 `boot.py` 的函数体里、`other` 类别仍
   在、kernel 与 loader 的边界还没分）——搬过来第一件事就是拆；拆不比写便宜，
   还多一层"这块是从哪来的"的阅读负担；
3. **边界已经定死**（0042：core / loader / launcher 三层 + 删减清单），从零写有
   明确的"写完的样子"，不再需要 P3 当脚手架。

**B. 只重写基座，能力插件照搬。** 否决：界限划不动——能力插件长在 P3 的 kernel
语义与 components 实现之上，搬它们等于搬半个 P3。

## 后果（如实记下）

- **起步比"搬"慢**：P3 的 423 个用例不复用（只当"边角情况清单"查阅）；已踩过的
  坑可能重踩——**缓解**：坑都写在决策记录里，写每步前先读相关记录；
- **M2 / M3 的工作量是真实的**：llm 接缝与 provider、会话日志与投影、提示词装配、
  工具管线、web / cli / sdk 三个产品都要重写——这正是"实质化"的代价，接受；
- **不背 P3 的兼容包袱**：日志格式、配置格式、模块命名都可以重新定；P3 目录原样
  留在 P3，两边的会话数据不互通；
- **每个小步都留测试**：M1 结束时以 P4 自己的验收为准（不是"P3 的测试还绿"）。
