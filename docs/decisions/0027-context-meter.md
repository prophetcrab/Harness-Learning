# 0027 上下文仪表：先看见，再动手（容量 / 构成 / 缓存命中）

- 日期：2026-10-14
- 阶段：P3_Coding `_04_Context_Meter`（P3 第四个阶段；原计划的 `_04_Compaction` 顺延为 `_05`）
- 状态：已采纳

## 背景

原计划 `_04` 直接做压缩。开工前调整了顺序：**先做仪表**。理由是压缩的三个决策
都需要"先看见"：

1. **什么时候压** —— 阈值要对"容量与使用"有可靠读数；
2. **压什么** —— 要知道是哪类内容在吃上下文（实测：工具说明书占 77.6%，消息只占
   14.8%——如果不知道这个，很容易把优化方向搞反）；
3. **值不值** —— 重发历史的实际成本取决于**前缀缓存命中率**（命中部分便宜得多）。
   实测发现我们的命中率是 **0%**，原因见下面的"重要发现"。

## 决策

**1) 两个信号，一个缩放：占比来自估算、总量来自实测。**

- **实测**：响应里的 `usage.prompt_tokens` = 模型这次真看到了多少。最可信，优先用。
- **估算**：不引 tokenizer（不引依赖），按 DeepSeek 官方经验比例（中文 ≈ 0.6/字、
  其他 ≈ 0.3/字符）把请求拆成四类：消息 / 系统工具 / 系统提示词 / 其他。
- **缩放**：四类估算按比例缩放到实测总额，余数给最大项——于是
  **"四类之和 == used" 是硬断言**（不受舍入影响），占比与总量各取所长。

没有实测时（离线 provider / 首个请求前）全用估算，并在页面上**标注来源**
（`used_source`）——不假装精确。

**2) 缓存命中率用加权平均。**

`Σhit / (Σhit + Σmiss)`，不是各次命中率的算术平均——那样一个 100-token 的
小请求会和 10000-token 的大请求等权。provider 不报缓存字段时显示"—"
（`cache_reported` 判定），**不假装 0%**：0% 是"报了但没命中"，"—"是"没数据"，
两者含义完全不同。

**3) 观测挂在 `llm/request` 瀑布与 `llm/response` 广播上。**

前者拿请求（算构成），后者拿响应（拿实测与缓存）。都是装载期订阅 → 卸载自动退订，
与 token-usage 的记账方式一致。

**4) 挂载走通用契约（与 token-usage 相同）。**

服务自报地址（`endpoints["context-meter"]`），主界面据此把「📐 上下文」按钮挂到顶栏、
iframe 内嵌页面。主界面不认识这个插件——**第二个"自报地址"的服务验证了这条规则的
通用性**（第一个是 token-usage）。

## ✅ 发现并修复：前缀缓存与每步重渲染冲突（命中率 0% → 74.2%）

实测数据（真实 DeepSeek，同一前缀连发三次）：

| 场景 | prompt | hit | miss |
|---|---|---|---|
| 固定系统提示词，160 tokens | 160 | 0 | 160 |
| 固定系统提示词，1112 tokens（第 2、3 次） | 1112 | **896** | 216 |
| 系统提示词含变化的时间戳（每步重渲染），167 tokens | 167 | 0 | 167 |

两个结论：

1. **缓存需要足够长的稳定前缀**才触发（160 tokens 太短不命中；1112 命中 896）；
2. **每步重渲染系统提示词（含 `{{time}}`）会让前缀缓存永远失效**——因为前缀的
   第一个字节就变了。

这是 `_02`（每 step 渲染，为了"模型每步都看到准确时间"）与缓存经济性之间的
**真实张力**。

**已在 `_04` 内修复**：给运行时上下文加 `{{date}}`（一天内不变），默认提示词由
`{{time}}` 改用 `{{date}}`；`{{time}}` 保留为"显式引用即自担成本"的能力。
修复后实测：**平均命中率 0.0% → 74.2%**（hit 7680 / miss 2671）。

这条修复的意义不止于省 token：它把"重发历史"的边际成本降了一个量级，
而 `_05` 压缩要解决的正是"重发历史太贵"——两者互补（缓存省钱，压缩省窗口）。

## 备选与排除理由

1. **引入 tokenizer 精确计数**。排除：多一个重依赖（tiktoken 等），而仪表的
   目的是"占比与趋势"，实测总额已经提供精确锚点；估算 + 缩放足够。
2. **四类按实测绝对值展示（不缩放）**。排除：估算与实测必然有偏差，不缩放会出现
   "四类之和 ≠ 总额"的尴尬；缩放让内部自洽，且占比（真正要看的）不受影响。
3. **缓存命中率用算术平均**。排除：见决策 2——会被小请求误导。
4. **把仪表做成 webui 的一部分（而非独立插件）**。排除：仪表要观测的是
   `llm/request` 与 `llm/response`，属于能力层；做成插件才能"装载即生效、
   卸载即停"，且与 token-usage 对称（两个都可以单独装卸）。

## 后果

- **收益**：上下文使用"看得见"（容量、四类构成、缓存命中）；主界面顶栏两个按钮
  （📐/📊）都是端到端可用的；卸载即停、端口释放；揭示了一条真实的性能问题
  （缓存 0% 命中），并把证据留档。
- **约束与已知边界**：
  1. **估算是近似**：比例来自官方经验值，不同内容（代码/JSON）偏差更大；
     但它只影响"占比"，不改变实测总额；
  2. **只有一类 provider 报缓存**（DeepSeek 系）；OpenAI 兼容协议的
     `prompt_tokens_details.cached_tokens` 未映射（需要时再加）；
  3. 页面每 2.5 秒轮询 `/api/context`，无推送（与 token 页面一致）。
- **债务与后续**：
  1. **缓存命中冲突**（上面的"重要发现"）——`_05` 压缩阶段处理；
  2. 未做"历史趋势"（每次调用的占比变化曲线）；
  3. 摘要/压缩后，"消息"类的占比变化应能通过本仪表观察到——那将是 `_05` 的
     一个现成验收手段。
