# 0016 事件流跟随：follow = 重放 + 订阅，断线补齐靠日志

- 日期：2026-10-09
- 阶段：P2_Coding/_11_Session_Follow（学习计划 M7 第二步，**M7 收官**）
- 状态：已采纳

## 背景

`_10` 把 harness 做成了服务（请求-响应：`initialize` / `session.prompt`），
但服务化还差一半：**客户端看不见"过程"**。一个 turn 可能跑好几秒（多次模型往返、
工具执行），请求-响应模型下客户端只能干等一个最终 JSON；更糟的是——服务端是常驻的，
**客户端会断线**（关掉终端、网络抖动），断线期间发生的事件怎么补？

学习计划 M7 的验收写得很具体："两个终端 serve + attach 共享同一会话；kill attach
后重连能补齐缺失事件"。dsh 的对应物是 `packages/client/connection/`（流式跟随、重连）。

## 决策

**1) `follow = 重放 + 订阅`，而且"补齐"不需要任何新机制**（`server/service.py`）：
`session.follow(from_seq)` 先把日志里 `seq > from_seq` 的既有事件逐条推给订阅方，
再把它登记为实时订阅——**重放结束的 `latest_seq` 正是订阅起点**，两段严丝合缝。
断线重连时客户端带上"已见最大 seq"作为 `from_seq`，断线期间的缺口就由**重放**补上。

这条等式的深意在于它**不发明任何东西**：补齐能力不是另建的缓存/队列，而是既有
"日志是唯一真相"（铁律 #1）的直接红利——事件本来就在 JSONL 里、本来就有单调 seq、
本来就能从任意点重放。服务化因此不需要"为丢消息而设计"，只需要"为可重放而设计"。

**2) 推送时机：事件产生即推 + 请求处理后兜底**（两条通路）：
- 打开会话时挂 `on_event` 回调：主循环每记录一条会话事件就 `flush()` 一次——
  长 turn **进行中**订阅者就能实时收到（不是等 turn 结束批量给）；
- 每次 `dispatch` 结束兜底 `flush()`：覆盖 A 连接上的 prompt 产生的事件要推给
  B 连接的订阅者（测试 `test_two_clients_share_one_session` 钉住）。

**3) 多连接 + 订阅台账**：服务是被所有连接共享的单例。订阅记录各自的 sender
（往哪个连接写）；`dispatch` 用可重入锁串行化（会话表/订阅表是共享状态）；
transport 的 `on_close` 在连接断开时调 `service.drop_sender` 注销它的订阅——
死订阅不会留在服务里（这也是重连能"当新连接处理"的前提：旧连接不留任何状态）。

**4) 传输层加"主动推帧"出口**：`LineTransport` 把自己的 `send(frame)` 回调传给
`dispatch`——重放与实时推送和响应帧共用一个写路径（顺序 = 调用顺序，天然满足
"重放先于响应"），并且写有锁（推送可能来自另一个线程，与响应不交错）。

**5) TCP 视为"多了一条连接来源"，不是新协议**（`server/tcp.py`）：每个 socket
连接起一条 `LineTransport`——与 stdio 完全同构的收发/错误/推送逻辑整条复用。
stdio 仍是默认（单客户端、无端口）；`--listen` 才开 TCP。

**6) 客户端侧 `attach.py`**：流式渲染（事件 → 人话）、提示符可继续发 prompt、
断线自动重连（重连时 `from_seq = last_seq`）。手工验证路径即 README 的三步：
跟随 → 断开 → 重连看补齐。

## 备选与排除理由

1. **轮询（客户端定期拉取新事件）**。排除：延迟与请求量都劣于推送；而且"拉取"
   在语义上就是"从 from_seq 重放"，只是把服务端的 flush 换成了客户端的定时器——
   不做推送而做轮询，等于用更差的性能实现同一语义。
2. **服务端为每个订阅缓存一份"未确认队列"**。排除：这才需要真正的补齐机制，
   且队列的持久化/清理/多订阅一致性都是新问题；日志重放把这些问题全部消掉
   （"从任意 seq 重放"本来就是对所有订阅者统一的答案）。
3. **WebSocket / SSE 起步**。排除：TCP 换行 JSON 与本项目既有的 stdio 协议零差异
   （同一条 LineTransport），升级成本最低；WS/SSE 是面向浏览器的产品化选择，
   学习目标（跟随语义）已经完整。
4. **每个连接一个独立服务实例**。排除：那就没有"两个终端共享同一会话"——会话
   缓存、事件推送都必须跨连接共享（服务是单例，连接只是它的"出线口"）。
5. **断线自动补齐由服务端记住"上次推到哪"**。排除：服务端替客户端记断点，多客户端
   就会互相打架；断点是**客户端自己的状态**（它见到了多少），由它重连时携带
   （"at-least-once + 客户端去重"的标准姿势；我们的 seq 天然支持幂等去重）。

## 后果

- 约束：事件推送的实时性依赖 `on_event` 挂得早（`_open_session` 时挂，覆盖该会话
  全部事件）；订阅是进程内的（服务重启后客户端重连重放即可，无持久订阅概念）。
  TCP 模式每连接一线程；`HarnessService` 的会话/订阅表变更全在锁内。
- 收益：**"kill attach 后重连补齐"成为可执行测试**（`test_reconnect_fills_gap_exactly`
  断言缺口事件"连续性 + 无重复 + 含断线期间的 turn 边界"）；多客户端共享会话、
  实时流、from_seq 过滤、断开注销全部有测试；golden 钉住帧形状与
  重放 → 响应 → 实时的帧序。59 个用例（22 基线 + 37 新增）。
- 债务与后续：
  1. **无背压**：订阅者写得慢时推送会阻塞产生事件的那个线程（本项目的量级够用；
     真要产品化需要每订阅一个发送队列）。
  2. **重连的幂等去重**：客户端按 seq 单调过滤（`seq > last_seq` 才渲染），
     重放与已见事件的重叠天然被滤掉——但客户端若换了新的 attach 进程，
     去重依赖调用方传对 `--from`。
  3. **HTTP/WS 未做**（沿袭 `_10` 的范围裁剪）；协议层对此无额外假设。
