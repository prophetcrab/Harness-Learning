# 0023 自扩展工具：让模型装卸自己所在进程的插件（白名单 + 审批）

- 日期：2026-10-14
- 阶段：P3_Coding `_01_Self_Plugin_Tools`（P3 的第一个阶段）
- 状态：已采纳

## 背景

P3 的插件底座（决策 0020）让"能力"可以运行时装卸，但只有**代码**能调用
`ctx.load_plugin/unload_plugin`——模型碰不到。这与"自扩展 agent"的目标之间
只差一层工具包装，但那一层里有两个必须回答的安全问题：

1. **装什么？** 内核只认插件**对象**；若把"从磁盘加载任意 .py"接进来，模型
   就等于拿到了任意代码执行权（它能给自己加能力，也能拆掉审批防线）。
2. **卸什么？** 不是所有插件都能随时卸：卸载 `webui` 会切断正在对话的网页连接
   （它就是这个会话的传输通道），卸载 `tools` 会让整个工具面消失。

同时参考 dsh 的做法（`packages/extensions/tool-cordis`）：它是"给模型一块
隔离沙箱 + 只读的自身视图"——动态包只活在内存、版本不可变、不改仓库与配置；
自身装配由启动时配置决定，`plugin-inventory` 明确只读。我们选择了**更直接**
的路线（对自身动手术），因此必须用别的手段补上它没有的那部分风险控制。

## 决策

**1) 三件工具 + 一个同名服务**（`plugins/self_tools.py`）：

    list_plugins    只读台账（名字/状态/依赖/能否卸载）+ 两份白名单 + 当前工具面。无需审批
    load_plugin     装载白名单里的插件。需审批
    unload_plugin   卸载白名单里的插件。需审批

工具是 `SelfToolsService` 的薄包装——逻辑都在服务里，测试可以直接打服务层。

**2) 两条白名单，方向相反**：

- **可装载（catalog）**：`插件名 → 工厂函数` 的显式映射，默认
  `clock` / `webui` / `rpc`。模型给的是**名字**，装配方给的是**代码**；
  本实现没有磁盘发现，所以模型无法凭空引入代码。
- **可卸载（unloadable）**：默认只有示例插件 `clock`。理由见背景第 2 点——
  卸载正在承重的插件会破坏当前会话；要放开哪些名字，由装配方显式决定。

**3) 装卸都需审批**（`needs_approval=True`，与写文件、跑命令同级）：
策略没配或人拒绝时 fail-closed，什么都不发生，工具返回结构化拒绝。只读的
`list_plugins` 不设审批——让模型能放心自查，不打扰用户。

**4) 效果对"下一轮"生效的说明写进返回值**：工具面在会话打开时快照
（`HarnessSession.ask` 每轮取 specs，因此**同一会话的下一步就能用新工具**）；
返回值里明确提示"新工具从下一轮开始可用"，避免模型在同一个 step 里就试图调用它。

**5) 可观测三件套**：`plugin/loaded` / `plugin/unloaded` 内核事件（供 RPC 跟随
与界面订阅）；工具调用本身进会话日志（`tool/result`）；返回值如实列出
"新增/移除了哪些服务与工具"。

**6) 示例插件 `clock`**（`plugins/clock.py`）：不是默认装配的一部分，只在白名单
里留名。装载它 → 多 `clock` 服务与 `now` 工具；卸载 → 全部回卷。选"时钟"是因为
它自包含、只读、无副作用——装卸它不会破坏任何东西，适合当第一个演示对象。

## 备选与排除理由

1. **支持"从目录发现并加载 .py"**。排除：那正是任意代码执行的入口；模型的
   装载参数会被当成"路径"而不是"名字"。自扩展的第一版必须让"能装什么"完全
   由装配方决定。
2. **不设白名单，改成"所有已注册插件都可装卸"**。排除：卸载承重插件（webui /
   tools / agent）会当场破坏会话，而这属于"用户按错一下键盘"就触发的破坏；
   显式白名单让危险操作变成需要主动配置的决定。
3. **装卸不设审批（靠白名单兜底）**。排除：白名单限"范围"，审批管"时机"——
   装个 webui 会开端口、装 rpc 会开监听，用户应当在场知情。与写文件同级是
   一致的尺度。
4. **做成"模型直接写插件代码并加载"**。排除：等同赋予代码执行权；且与 dsh
   （沙箱内动态包）不同，我们**没有沙箱**。留待将来真有沙箱时再评审。

## 后果

- **收益**：模型可以自查运行时（列台账）、按需扩展自身（装工具/服务）、
  且所有动作都在白名单与审批之内、全程留痕。真实运行验证了完整闭环：
  `list → load(clock) → now（新工具下一轮可用）→ unload`。
- **约束与已知边界**：
  1. **无沙箱**：白名单之外的插件不存在"安全装载"通道；这是设计边界。
  2. **同步执行**：装卸在管线的工作线程里同步跑（内核访问仍是串行的——同一
     时刻只有一个 turn）。
  3. **卸载即断连**：白名单默认排除了 webui——若装配方把它加进去，卸载后
     当前页面会失去连接（服务已停）。这是语义必然，不是 bug；README 有说明。
  4. **无持久化**：装卸只作用于当前进程；重启回到装配时的状态（与"每次启动
     重新组装"的既有语义一致）。
- **债务与后续**：
  1. 白名单目前是构造参数（默认常量）；将来可随 P2 的配置分层一起做成
     配置项（`profiles/*.yaml` 里的 `selfTools.catalog` 之类）。
  2. 没有"装卸历史"查询工具（会话日志里有工具调用记录，但没有专门的
     `plugin history` 视图）；RPC `session.follow` 的订阅者目前能看到
     `plugin/loaded` 事件，界面暂未专门渲染。
