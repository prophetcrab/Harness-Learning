# 0055 批量脚本改源码的教训：不在未提交的工作区上做机械重写

- 日期：2026-10-19
- 阶段：P4_Coding（M2 收尾后 / M3 起步前）
- 状态：已采纳

## 背景

为了把能力插件对基座插件的 import 改成"本地副本 + 字符串常量"（后来收紧为
0053 的单向依赖），我写了六个一次性批处理脚本：`_decouple.py`、`_copy_defs.py`、
`_repair_parens.py`、`_repair2.py`、`_repair3.py`、`_rebuild_imports.py`。

这些脚本用正则 / 行扫描去删 import、复制定义块、补闭合括号。结果：

- 把 `ctx.provide("service", value)` 的服务名参数删掉，留下 `ctx.provide(value)`；
- 把 `ctx.emit(EVENT, ...)` 的事件名删掉，留下 `ctx.emit(request=...)`；
- 把 `KNOWN_EVENT_TYPES`、`BUILTIN_MODES` 这类定义块掏空；
- 把 `traces.append(...)` 塞进别的函数调用里，造成语句嵌套错位；
- 删掉 `import json` / `import sys` / `import urllib.*` 等跨文件依赖。

更糟的是：**这些插件当时都还没有提交过 git**（`plugins/` 下只有旧位置的
`loader.py` 在版本库里），所以没有任何可回退的基线。解包工具也不支持
Python 3.13 的字节码。用户当时的处理是：**"你重写吧"**。

## 决策

**停止一切"批量机械改写源码"的做法。** 具体三条：

1. **先提交，再重构**：任何跨文件的机械改动之前，工作区必须有一个可回退的
   基线提交（或者至少能 `git stash` / 从暂存区取回）。
2. **改源码用编辑器逐个改，或重写整个文件**：AST 级批处理只在"输入输出都能
   被完整验证"时使用（例如生成报告、统计），不用来改源码。
3. **用测试当护栏，而不是用脚本的自我检查**：每修一个文件就运行对应的定向
   测试；全绿再下一个。恢复顺序按依赖方向：base → fs 策略 → llm → proc →
   prompt → session → tools → agent → workspace。

## 备选与排除理由

**A. 用脚本修脚本（继续写 `_repair4.py`）**。已经被证明会让损伤扩散：每次
"补括号"都在制造新的错位，而且错误是静默的（语法合法、运行才炸）。放弃。

**B. 从 PyPI 找反编译器恢复 `.pyc`**。环境是 Python 3.13，主流反编译器跟不上；
而且恢复出来的代码可读性差，等于把技术债固化。放弃。

**C. 直接重写全部能力插件**。最终采用的就是这个：按模块职责手工重写，类型
副本与字符串约定重新对齐，测试逐个变绿。代价是时间，收益是每一行都重新
理解过一遍。**采纳**。

## 后果

- 六个一次性脚本已删除（不在版本库里留"能再次造成损伤的工具"）；
- 恢复后全量 **500 用例**再次全绿，真实 DeepSeek API 回归通过；
- 恢复过程中顺手补上的东西已单独记录：插件级 `requires` 在 loader 里真正
  执行（0052 提到过、实现漏了）、`llm-provider` 的 `base_url` 接受服务根地址
  并补 `/chat/completions`；
- 教训进入工作纪律：**先提交基线，再动跨文件重构；改源码不用批量脚本**。
