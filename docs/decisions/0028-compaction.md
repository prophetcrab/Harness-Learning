# 0028 上下文压缩：日志只追加"折叠声明"，投影里旧区段变一条摘要

- 日期：2026-10-14
- 阶段：P3_Coding `_05_Compaction`（P3 第五个阶段）
- 状态：已采纳

## 背景

长会话迟早撞上窗口上限。`_04` 的仪表给出了"什么时候该动手"的读数，
`_05` 要动手：**把旧区段压掉，让对话能一直继续下去**。

两条铁律夹住了实现空间：

- **#1 模型可见即已记录**：历史只能由日志投影而来，不能凭空造一条"摘要消息"；
- **日志 append-only**：压缩**绝不能**删改已有事件（删了就没有重放、没有对账、
  没有崩溃修复的意义了）。

于是问题变成：怎样**只追加**，却让投影出来的历史变短？

用户同时定下了比例：**90% 触发、尾巴留 10%**（原提议 70%/30%、再议 90%/10%）。

## 决策

**1) 追加一条 `compact/checkpoint`，按"位置"折叠投影。**

checkpoint 的内容是一句声明："写我的时候，对话列表最前面的 `folded` 条已经
折成这句摘要"。投影读到时丢掉那 `folded` 条、把摘要顶到最前。

- **为什么按位置而不是按 seq**：初版实现按 `seq ≤ folded_upto` 丢。但摘要自己
  带一个更大的 seq 坐在列表最前，列表的 seq 因此**不再单调**——"折 1 条"实际
  掉了 3 条，内存历史与日志投影当场失同步（实测踩到，录制器直接报
  "压缩条数超出当前对话消息数"）。改为按位置丢后，投影与循环内存里的切片
  `history[start : start+folded]` 逐条对应，两个视图天然对齐。
- **摘要的形态**：一条 `user` 消息，正文带前缀 `【早前对话摘要】`。放最前、
  且下一次压缩会把它连同尾巴一起再折进去——**摘要不堆积、不链式膨胀**。
- **越界即报错**：`folded` 超过当时的消息数 → 投影当场抛错（日志被外部改过
  就不该假装能读；静默夹紧会让"重放同构"变成一句空话）。

**2) 触发用量 = `max(字符估算, 上次实测 prompt_tokens)`。**

实测最可信，但它来自**上一个**请求；本请求只会更大（多了一轮回复与工具结果）。
取 `max` 是保守的一侧——宁可早压一点，不要撞窗口。`used_source` 如实标注来源。

**3) 阈值 90% / 保留 10% / 摘要 ≤5% 容量。**

压完落在 15%~20%，离下一次触发很远。压缩必然打断一次前缀缓存（前缀变了），
所以**次数越少越好**——这是"少压、压稀"的取向，与"频繁小压"相反。

**4) 当前 turn 永不折叠（`floor` 钳位）。**

折叠区止步于本 turn 的第一条消息：刚问的问题、刚拿到的工具结果不能在
"干活干到一半"时被摘要掉。切点被钳在 `floor` 之前（`cut <= floor`）。
代价：**一个 turn 内部疯长时压不动**——那是 `_07`（大输出转存）的题目。

**5) 切点成对安全。**

`assistant(tool_calls)` 和它的 `tool` 结果必须同去同留：切点若落在 `tool`
消息上就向左退一步。劈开配对下一轮请求会被 API 直接拒绝。

**6) 压缩在每 step 发请求前做（turn 中间也做）。**

只在 turn 开头检查会漏掉工具往返带来的增长。

**7) 失败即放弃（fail-soft）。**

摘要调用出错/返回空 → 只发一条瞬态 `compact_failed`（**不进日志**——什么都没
发生，不是事实），本轮照常继续，下次超阈值还会再试。压缩永远不能把对话搞死。

**8) 摘要请求：摊平成文本的一次普通模型调用。**

不把折叠区的消息原样发去摘要——很多供应商要求"带 `tool` 消息就必须同时带
`tools` 声明"，摊平谁都能读，顺带把超长工具结果裁到每条 2000 字符。
裁剪取法是"第一条 + 从最新往回填"：第一条通常装着用户的原始目标。
**摘要调用同时走 `llm` 服务**——所以它会被 `_03` 的账本记一笔、被 `_04` 的
仪表看见：压缩的代价必须可见，不能偷偷花。

**9) 默认窗口 64K → 1M**（用户指定）。

`DEFAULT_CONTEXT_WINDOW = 1_048_576` 上移到 `components/context/tokens.py`，
入口、仪表、压缩三处共用同一个默认值。

## 备选与排除

1. **直接删旧事件**（"真删了更省事"）。排除：毁掉重放/对账/崩溃修复的整个
   价值基础；而且崩溃修复会把这些删除当成"坏尾"处理的假设也不再成立。
2. **把摘要写进 `session/start` 或改 system 提示**。排除：那会改写既有事实，
   且把对话内容塞进 system 会破坏前缀缓存的稳定前提。
3. **在日志里存"压缩后的消息数组"快照**。排除：又多了一份"真相"，
   与"历史由日志投影"的纪律冲突。
4. **摘要后立刻再检查一次、循环压到阈值以下**。排除：单条巨物（如超大工具
   结果）会让循环压不动也压不下去；`_07` 才是它的正解。现在压一次就放行。

## 后果

- **收益**：长会话能一直继续；日志**一条不改**、seq 严格递增、重放逐条同构；
  压缩在界面上可见（折叠徽标 + 摘要全文 + 事件流摘要行）。
- **实测（真实 DeepSeek，窗口 2200 强制压缩）**：5 次压缩，每次
  `folded` 1~6 条、`before` 2200~2500 → `after` 620~770 tokens；
  日志 `user/message` 6 条一条没少。第 4 轮模型如实回答"我手头没有第一句话的
  原文，只有一份早前对话摘要"——它**知道自己看到的是摘要**。
- **约束与已知边界**：
  1. 摘要**有损**（所以尾巴留 10% 原版；摘要被要求保留目标/决定/路径/待办）；
  2. 压缩**打断一次前缀缓存**（刻意的取舍，靠"稀触发"把次数压到最低）；
  3. **单个 turn 内疯长压不动**（当前 turn 保护优先于压缩）；
  4. 估算不是 tokenizer（触发判断有误差，实测一侧会持续纠偏）。
- **债务与后续**：`_07_Spill` 处理"单个巨大工具结果"；`_06` 起按垂类裁剪。
  整合包 `mini_harness/` 已按 PLAN 的"重生成时机"同步为 `_05` 完成态。
