# 0020 P3 基础包：把整个 harness 重表达为插件（内核 + 构件 + 插件三层）

- 日期：2026-10-13
- 阶段：P3_Coding（首个里程碑：基础包）
- 状态：已采纳

## 背景

P3 的路线定位是"补齐常规 harness 能力（流式、预算计量、压缩、任务管理…），
范围由垂类裁剪"，且明确"**垂类必须在 P3 之前定死**——不定，P3 会变成
'我全都要'然后烂尾"。路线图把 P4 标为"重构"（把 P3 的能力改写成插件）。

本次任务改为先做地基：**在 P3 主目录下交付一个"完全插件化的 mini harness"
作为基础包**。这把路线图里 P4 的内核目标提前，理由是它不受垂类决定影响——
无论垂类是什么，能力都要挂在一个内核上；先有底座，P3 后续的能力增量才有
统一的落点（否则每加一个能力都要动装配代码，P2 的配置树+工厂模式已经显露
这个瓶颈：依赖关系是隐含的、错的装配顺序要到运行时才炸、没有卸载通道）。

## 决策

**1) 三层分离，依赖单向**：`kernel`（插件内核，纯逻辑）→ `components`（纯构件，
不 import kernel）→ `plugins`（能力插件）。`components/` 的代码来自 P2 冻结
基线（P1/P2 沉淀的构件），是**唯一搬运进来的部分**；改动的只有 import 路径与
两处小升级：`ToolRegistry.unregister`（插件卸载要能回卷外部注册表）、事件表加
`system/message`（把 P2 `_02` 的扩展合并进投影，不再需要子类 Session）。

**2) 内核五件套（服务 / 事件 / effect / inject / 插件）**：这是本包与技术
路线图 P4 的对应物。相对 P2 `_07` 的 Context，新增：

- **事件**：`on`（订阅，返回退订函数）、`emit`（广播）、`waterfall`（可改写
  值的中间件链）——`prompt/variables` 与 `llm/request` 两个瀑布是插件协作点；
- **inject 依赖装载器**：插件声明 `inject = ("fs",)`；**装载顺序无关**
  （依赖齐备即激活，缺失保持 pending）；提供者被卸载 → 依赖者**先**退位、
  提供者回来 → 自动重新激活。P2 的 `load_plugins` 只按列表顺序装载、失败回卷，
  没有依赖语义。

**3) 插件 = 有 setup(ctx) 的对象（可声明 name / inject）**；服务是"命名单槽 +
显式 require"，与 P2 的单槽 ServiceContainer 同款，但登记的撤销交给 effect
自动管理（"注册即 effect"）。

**4) 能力全部插件化，装配 = 插件列表**：七个标准插件（llm / fs / proc / tools /
sessions / prompt / agent），`boot_offline` / `boot_realtime` 是两个标准组合。
P2 的 YAML 配置分层（`profiles` / `--dump-config`）**不移植**——它是"配置数据 →
插件"的一层，应该在 P3 内核上重做（见"后果/债务"）。

**5) 与 P2 的兼容边界**：P2 `mini_harness/` 作为成品快照保留不动（其 66 用例
继续可跑）；P3 基础包是 P2 能力的**插件化重表达**，不追求与之二进制兼容。
两边的顶层包名大面积同名（`kernel`/`prompt`/`context`/`chat`/…），依靠各目录的
conftest 做导入隔离（P2 已有的机制，P3 照抄一份）。

## 备选与排除理由

1. **在 P2 的 `harness/` 上打补丁，而不是重表达**。排除：P2 的基线是"冻结"
   约定（各阶段 copy 起点），改它会破坏 P2 已成文的快照纪律；且"插件化"就是
   要一次把结构做对，打补丁会留下两套装配方式长期并存。
2. **引入第三方 DI/插件框架（如 dependency-injector、pluggy）**。排除：本
   项目的目标是"理解机制"，核心 > 依赖；cordis 的思路（服务仓库 + effect +
   inject）用几百行就能表达本题所需的最小版本，且与 dsh 的对照更直接。
3. **引入异步（asyncio）事件与 effect**。排除：现有全部构件是同步的（循环、
   管线、日志、RPC 都同步）；为"内核更像 cordis"引入异步会污染整条链路，
   得不偿失。异步留待真有并发需求时再评审。
4. **第一步就做配置分层（YAML → 插件）**。排除：先证明内核本身成立（服务 /
   effect / inject / 热插拔），配置层是它的消费者；顺序反了会在内核不稳定时
   反复重写配置解析。

## 后果

- **收益**：能力装配从"隐含在装配代码里"变成"内核可检查、可回卷的事实"。
  已被测试钉住的性质包括：装载顺序无关、依赖退位/重激活、批量装载失败零残留、
  卸载回卷（服务 + 订阅 + 外部注册表）、装配单可由日志重建、MemoryFS 零磁盘痕迹。
  运行时可热插拔（demo 第 4 节：卸 fs → tools/agent 自动退位；换 LocalFS → 自动重激活）。
- **约束**：
  1. `plugins/tools.py` 的"工具面注销"是**手工 dispose**（ctx 管不到外部注册表
     的内部状态）——这类插件必须自己写撤销动作，是"注册即 effect"的例外路径，
     代码里有注释标明。
  2. 依赖检查是"服务名存在性"，无版本约束；**环形依赖**不会死循环（成组退位），
     但语义未定义——若将来出现真实的环形需求，需要给 inject 加环检测。
  3. 退位 cascade 期间用 `_suppressed` 抑制重激活（否则依赖者会在提供者槽位
     尚未撤销的窗口里被立刻重新装回去）；这是实现细节，但对"卸载时机"的语义
     有影响，已在 kernel 注释里写明。
- **债务与后续**：
  1. **配置分层待重做**：P2 的 `profiles/*.yaml` + `--dump-config` 应在 P3
     内核上重表达为"配置 → 插件实例"，补回"一行 patch 换 provider"与来源台账。
  2. **服务化（RPC / follow / webui）未移植**：属于平台档；在插件内核上重做时
     可以把"服务端"本身做成插件（`ctx.provide("rpc", ...)`）。
  3. **垂类仍未定**：本包刻意保持"通用最小"。P3 的能力清单（流式、压缩、任务
     管理等）继续等待垂类裁剪；底座不阻塞这件事。
