# 0057 两级门禁：离线绿与真实 API 绿必须分开汇报

- 日期：2026-10-20
- 阶段：P4_Coding（M3）
- 状态：已采纳

## 背景

用户问：**"你为什么总倾向用假 api 进行测试？"**

核对后发现两件事：

1. **默认门禁一直是离线的**。`tests/conftest.py` 把 `real` 标记的用例默认跳过，
   只有显式 `--real`（或 `P4_REAL_API=1`）才运行。所以每次说"全绿"，实际
   含义只是"离线全绿"——34 条真实 DeepSeek 用例根本没跑。
2. **离线测试存在自我实现的循环**。`manifests/minimal.py` 的
   `_offline_transport` 返回的 SSE 是按我们自己的解析器假设手写的；它验证的是
   "解析器能解析自己编造的数据"。如果真实接口的字段形状漂移，离线测试照样绿。

离线测试本身没有错——确定性、速度、成本、CI 无凭证都是真实理由。问题出在
**汇报口径**：把两套门禁合并成一句"全绿"，掩盖了真实契约没有验证这件事。

## 决策

**保留两套门禁，永远分开计数、分开汇报。**

| 门禁 | 命令 | 模型 | 频率 |
|---|---|---|---|
| 离线门禁 | `pytest tests -q` | 剧本（不联网） | 每次改动 |
| 真实 API 门禁 | `pytest tests/test_real_api.py --real -q` | DeepSeek 真实接口 | 里程碑节点 / 阶段收尾 |

### 汇报规则

- 说"通过"时必须带门禁名与数字：
  - `离线门禁：536 passed, 34 skipped`
  - `真实 API 门禁：34 passed`
- **禁止**只说"全绿"而不说明是哪一套；
- 只跑了离线时，必须补一句"真实 API 门禁未运行"；
- 离线结果里出现 `skipped`，就不能表述成"全部通过"。

为了让这条规则在工具层面可见，`pyproject.toml` 的 pytest 配置加了 `-ra`：
默认跑完会列出跳过原因，`34 skipped` 不会藏在汇总行里。

### 真实 API 套件的定位

它不是"可选的额外验证"，而是 **provider 契约的回归测试**：

- 离线套件证明框架逻辑正确；
- 真实套件证明适配器与 DeepSeek 的线格式、流式分块、用量字段、错误码
  分类没有漂移。

两者验证的东西不同，缺一不可。

### 假传输的唯一合法用法

`test_real_api.py::test_goal_retry_recovers_transient_failure` 在真实
`http_transport` 外面包了一层"第一次抛 `LLMConnectionError`"的故障注入。
这是刻意为之：要验证重试插件在**真实请求**上不重复输出，必须先制造一次
断线。网络层本身仍然是真实的，所以它仍算真实 API 用例（`34 passed` 里包含
这一条）。除此之外，真实套件里不出现任何假 provider。
## 备选与排除理由

**A. 把真实 API 用例并入默认门禁**。否决：CI / 无网环境会红，单次全量从
2 秒涨到 64 秒且每次计费；日常改动的反馈循环会被拖垮。

**B. 完全删掉离线测试，只信真实 API**。否决：真实模型输出不确定，没法断言
工具调用顺序、token 计数、错误路径；而且失败定位会被网络噪声淹没。

**C. 只改口头习惯，不动仓库**。否决：上一轮已经证明靠"记得说清楚"不可靠；
至少要有一个可检查的痕迹（门禁表 + `-ra`）让跳过数量显式出现。

## 后果

- README 新增「门禁与汇报口径」一节，给出两套命令与固定措辞；
- `pyproject.toml` 增加 `addopts = "-ra"`，跳过的真实用例在默认输出里可见；
- 当前基线：离线 **536 passed, 34 skipped**；真实 API **34 passed**；
- 真实 API 套件在里程碑节点运行，结果写进对应决策记录或阶段总结。
