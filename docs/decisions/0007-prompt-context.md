# 0007 运行时上下文：每 step 渲染、变化才记录、遮蔽式投影

- 日期：2026-10-08
- 阶段：P2_Coding/_02_Prompt_Context（学习计划 M4 第二步）
- 状态：已采纳

## 背景

`_01` 把系统提示词变成了"有序 section 装配出的文本"，但它仍是**静态**的：装配只发生
一次，文本写进 `session/start` 后就冻结了。M4 明确要求"运行时上下文每 step 渲染；
`system/message` 进日志"，即让提示词里的 `{{cwd}}` / `{{platform}}` / `{{time}}`
在会话进行中"活"起来。这一步有三个硬约束：

1. **`harness/` 冻结**（P2 组织约定）：不能去改 `AgentLoop` 加钩子，也不能改基线的
   事件类型表（它是封闭集合，未知类型直接 fail loud）。
2. **铁律 #1/#2**：模型每步看到的文本必须能从日志重建；日志只增不改——"更新提示词"
   不能重写 `session/start`。
3. **可确定性测试**：时间、路径、平台都是外部环境，测试必须能喂脚本化的取值。

## 决策

四件事，一件一层：

**1) 插值做薄**（`prompt/interpolate.py`）：`{{name}}` 的最小替换，只支持空白容错；
未知变量、非法名、非字符串值一律 fail loud（宁可渲染失败，也不让半个模板进日志）。
装配器扩展为 `assemble(variables)`，`parts()` 仍给出模板——"模板"与"渲染结果"分开，
为 `_03` 的"可由日志重建"断言留下接口。

**2) 上下文做快照**（`context/runtime.py`）：`RuntimeContext` 是不可变的三个字符串
（cwd / platform / time），由 `collect_runtime_context(workspace, now=…, platform_name=…)`
采集，`now` 与 `platform_name` 可注入。渲染保持**纯函数**（同快照 → 同文本），
"什么时候重新采样"是策略、归上层。

**3) 挂钩点选 provider 接缝**（`context/provider.py`）：`AgentLoop` 每个 step 恰好调一次
`provider.complete()`，而 provider 本来就是 M1 的接缝（任何满足协议的对象都能插进去）。
于是 `RuntimePromptProvider` 包装内层 provider：每步重新渲染 → 与"当前生效文本"不同则
回调记录 → 把请求里的 system 消息替换为最新文本。**循环一行不改**，"换 provider 不改
上层"的接缝价值在此第二次兑现（第一次是 FakeLLM ↔ DeepSeek 互换）。

**4) 用"遮蔽"表达更新**（`context/session.py` + `projection.py`）：新增事件类型
`system/message`（内容 = 一次渲染）；投影语义是"最近一次生效"，`session/start` 的初始
文本被后续 `system/message` 遮蔽——**日志一条不动，遮蔽发生在派生时**（铁律 #2 的第三次
应用：日志遮蔽、工具注册表遮蔽、section 遮蔽、现在是 context 遮蔽）。写入路径由
`ContextSession` 子类承担（基线类型走 `super()`，纪律不变）。

配套两个小决策：**渲染无变化不记录**（日志不留重复；"每步渲染"的事实保留在每步请求的
改写里，重建语义不受影响）；**resume 以日志里的生效文本为基线**（重开不重复记，
上下文真的变了才追加）。

## 备选与排除理由

1. **改 `harness/agent/loop.py`，在 step 循环里直接挂钩子**。排除：违反 P2「harness 冻结、
   机制放顶层」的组织约定；且循环本来就不该知道"提示词如何渲染"——接缝就是为了避免
   这种耦合。包装 provider 不动基线一行。
2. **每步都记一条 `system/message`（不去重）**。排除：时间每步都在走 → 每步都变 →
   日志迅速被无信息量的逐秒快照灌满；而"变化才记录 + 最近一次生效"的重建语义同样
   完整。dsh 的 time-context 也用 `refreshIntervalMs` 控制注入频率，同构的思想。
3. **更新时重写 `session/start` 的文本（或改写事件）**。排除：直接违反铁律 #2
   （日志只增不改）；"模型可见 ⟺ 已记录"要求的是**追加**新事实，而不是篡改旧事实。
4. **把渲染做成"每 turn 一次"**。排除：计划明确要求"每 step 渲染"；一个 turn 内多步
   （工具往返）期间时间真的在走，取舍精度明显更粗。
5. **上模板引擎**。排除理由同 0006：核心不是模板语法，且遮蔽/追溯语义还得自己做；
   四个变量的插值几十行就够。

## 后果

- 约束：`prompt/` 仍是纯逻辑（不依赖 harness）；`context/` 依赖 `prompt` + `harness`，
  方向单一。新事件类型的写入路径是 `ContextSession` 对基线私有状态（`_store` /
  `_events` / `_copy_event`）的**同构复刻**——这是本阶段最明显的债务。
- 收益：模型每步看到的文本可由日志完整重建（demo 第 0b 节与接线测试都有"实际收到的
  == 日志重建的"断言）；上下文采集可注入，测试全离线且确定性；作用域遮蔽（`_01` 机制）
  在渲染路径上原样生效。57 个用例（22 基线 + 35 新增），全项目 390 用例全绿。
- 债务与后续：
  1. **事件类型注册接缝**：目前只有 `system/message` 一个扩展类型，复刻可以接受；
     若 `_03+` 还要新增事件类型，应回头给基线补一个"事件类型注册"的正规接缝，
     而不是继续复刻私有写入路径。
  2. **webui 只看基线投影**：可视化页面仍按基线的 `derive_messages` 投影，会把
     `system/message` 当作未知类型跳过（显示为事件但不参与消息视图）。不影响本阶段
     验收（webui 属基线），后续如要展示"提示词演进"再补。
  3. `agent-instructions` / `session-reference` 等 dsh context 家族的其他成员
     （把 AGENTS.md、其他会话引用注入上下文）本阶段未做——它们共用同一套"每步注入 +
     持久化"的模式，模式已在本阶段立好。
