# 0018 P2 形态可视化页面：子类化基线 Handler，装配全部走配置

- 日期：2026-10-09
- 阶段：P2_Coding/_11_Session_Follow（收尾增补，不占阶段主线机制）
- 状态：已采纳

## 背景

项目从 P1 `_05` 起就有一个可视化页面（`harness/webui/`），它是"M1–M3 形态"的：
工具面直接从 `build_workspace_registry` 构造（只有 4 件：calculate + read/write/list），
provider 由 `build_deepseek_provider` 固定；**看不见** P2 的新机制——`shell` /
`edit_file` / `search_text` / `find_files`、插件 effect 台账、配置分层与来源层、
每 step 渲染的装配单。P2 全程的边界是"每阶段只加一个机制、`harness/` 冻结"，
页面升级不在任何阶段的验收里，因此拖到了收官。

## 决策

**1) 新页面放阶段顶层（`_11/webui/`），基线页面原样保留**：P2 的组织约定是
新机制在阶段主目录顶层、`harness/` 冻结。基线的 `harness/webui/` 继续存在且
继续被基线测试覆盖——它是"M1–M3 形态"的历史快照与回归对象；新包是"P2 全部机制
就位后"的当前形态。两个页面并存（基线 :8765、新页面 :8766 默认端口错开），
**不是替换而是叠加**——这条与项目对 `ServiceContainer`（`_04` 旧路径保留）
的处理方式一致。

**2) 实现方式是"子类化基线 Handler"，只覆盖装配点**：HTTP 协议细节、`/api/sessions`
列表、`/api/sessions/<id>` 详情、fork、模拟崩溃、静态页服务全部从基线继承；
本包只覆盖三处：

- `_api_config`：回 profile、插件台账、**每行的来源层**（`_09` 的台账）；
- `_api_tools`：从 boot 出的 `toolbox` 槽位取说明书（8 件工件而非硬编码 4 件）；
- `_api_send`：装配从 `MiniHarness.open` 换成 **`open_context_harness`**——
  与 `chat.py` 走同一条装配路径（可注入 `tool_registry`、每 step 渲染、
  装配单进日志）；于是"页面上跑一轮对话"与"命令行跑一轮"写到日志里的东西一致。

另加 `GET /api/ctx`：effect 台账 / 槽位 / 工具面计数——`_07` 的"注册即 effect"
第一次有了可视化出口。

**3) 前端在基线页面的副本上做增量**（v1 的 HTML 原样复制再改三处）：
头部加 profile 徽章（悬停显示每行 `id = name ← 来源层`）与插件台账行；
事件标签表补 `system/message`（`_02` 的提示词更新事件，展开显示引用变量）。
**不动**既有布局与交互（对话区、日志轨迹实时生长、回放/崩溃/分叉按钮）——
基线页面的产品度已经够用，本阶段只是把它接到新装配上。

**4) 配置驱动落到页面**：`--profile dev|prod` 选层、`--patch` 叠 CLI 补丁
（与 chat.py 同一套 `load_profile`）。工作区**不再有** `--workspace` 参数——
它来自配置树的 `toolbox.workspace` 行（"配置说了算"在参数层面可见）。

## 备选与排除理由

1. **直接改 `harness/webui/server.py`**。排除：违反 `harness/` 冻结约定，
   且会让"M1–M3 形态"的历史快照与回归测试一起消失——基线页面的存在价值
   恰恰是"对照"（同一个 harness，接上 P2 机制前后差什么，两个 URL 一比即知）。
2. **重写一个前端（换框架/换布局）**。排除：本阶段的目标是"接上新装配"，
   不是产品重做；既有页面（P1 `_05` 打磨过）的对话/轨迹/回放/崩溃/分叉
   全部保留为默认行为，改动面越小越可验证。
3. **页面内做审批 y/n**。排除（沿袭基线决定）：HTTP 请求线程里等人输入
   会把服务挂死；保持"默认放行 / `--deny-writes` 全拒"两档，是页面语境下
   诚实的选择（README 与页脚都写明）。
4. **把页面接进 RPC 服务（serve.py）作为前端**。排除：RPC（`_10`/`_11`）与
   页面（webui）是两条平行前端；统一它们（页面走 JSON-RPC + follow 事件流）
   是产品化课题，不在本阶段——现阶段页面直接用进程内 harness，简单可靠。

## 后果

- 约束：新页面与基线页面共享"页面=观察窗"的定位（不引入新机制）；新包只依赖
  既有顶层包（config/context/kernel/providers）与基线 webui，不反向被依赖。
- 收益：**P2 的全部机制在同一屏可见**——头部：profile + 来源层（悬停）+
  插件台账 + 8 件工具；对话区：工具调用可视化；轨迹区：事件流实时生长，
  含 `system/message`（提示词更新）与 `tool_count: 8`（新工具面真的进了模型请求）。
  浏览器实跑验证过（截图：`llm:fake · profile dev` + `插件：llm:FakeLLM · fs:MemoryFS
  · subprocess:ScriptedSubprocess · toolbox` + 工具列表 8 件）。
  7 个新测试（配置/台账接口、全工具面、发送流落盘、装配单、deny-writes、页面
  元素）全绿；全项目 763 用例全绿。
- 债务与后续：
  1. **前端仍是"读日志 + 进程内发送"**，没有走 `_10`/`_11` 的 RPC/follow——
     多客户端跟随（B 观众看 A 的实时事件流）在页面上尚未接线；接线点是
     `send` 的 NDJSON 流换成 `session.follow` 订阅（协议已就绪）。
  2. **页面默认自动放行审批**（与基线一致）；真实产品需要页面内审批交互
     （或走 `--deny-writes` 的白名单，而非 y/n）。
  3. **两个页面的默认端口不同**（8765/8766），README 已写明；未来若合并成
     一个页面，本包就是迁移起点。
