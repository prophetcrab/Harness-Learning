# 0005 mini harness 组装：接线而非新增机制，副本而非共享包

- 日期：2026-10-07
- 练习：P1_Coding/_05_Mini_Harness
- 状态：已采纳

## 背景

P1 前四个练习各自把一块机制做扎实，且都刻意守住了同一批接缝：

- `_01` 定义 `LLMProvider` 协议；
- `_02` 定义 `AgentLoop`（执行器契约 = `Callable[[str, dict], dict]`、事件流 = `on_event(kind, payload)`）；
- `_03` 的 `ToolPipeline.execute()` 恰好满足那个执行器契约；
- `_04` 的 `SessionRecorder` 恰好消费那个事件流，`Session.derive_messages()` 产出循环的初始历史。

于是 `_05` 面临一个选择：**组装时要不要引入新的抽象层**（比如一个统一的
`Component`/`Plugin` 协议、一个 service container、一个配置驱动的装配器）？

同时还有一个工程问题：每个练习都是**自包含**的（各带一份同名包副本），
全量测试靠 `conftest.py` 驱逐模块来避免串味。`_05` 收敛成单一 `harness/` 包，
能消除重复——但会打破"每个练习可独立运行/阅读"的约定。

## 决策

**一是组装只做接线，不新增机制。**

`MiniHarness` 是一个纯装配类：把 `Session`、`LLMProvider`、`ToolRegistry`、
`ToolPipeline`、`Runner`（其内含 `AgentLoop`）接起来，暴露 `send()`。它不定义
新协议、不引入容器/插件系统、不做配置解析。前四个练习的包**一行未改**。

`app.py` / `demo.py` / `env.py` 同样只是"入口 + 工具面 + provider 构造"，不含机制。

**二是保留各练习的自包含副本，不在此刻收敛成单一包。**

`_05` 也是自包含的：`llm_seam`(_01)、`agent_loop`(_04)、`tool_pipeline`(_03)、
`session`+`runner`(_04) 全部原样拷贝进来。收敛（去重成单一 `harness/` 包）
推迟到 M4 起启用正式包结构时（学习计划 §5 已注明）。

## 备选与排除理由

1. **引入插件/容器抽象再组装**。排除：那正是 dsh 的 `Cordis ctx.effect()` 那一层
   （M6 profile 组装的主题）。此处引入会**掩盖**"接缝本来就能直接对接"这一要验证的
   事实——本练习要证明的是四个已有接缝**零改动**就能合成产品，而不是"再加一层才
   能组装"。新增抽象留到 M6，那时才有真实的配置分层需求。
2. **收敛成单一 `harness/` 包，消除重复**。排除：会牺牲每个练习"单目录自包含、
   可直接阅读运行"的教学价值（P1 的核心约定）；且 M4 起才有正式包结构与门禁，
   此刻收敛属于提前优化。成本（几份副本 + conftest 驱逐）已被显式记录并接受。
3. **让 `MiniHarness` 直接接管日志（绕过 `Runner`）**。排除：`Runner`（_04）已经把
   "事件流 → 会话日志"这层接线做对了（含 resume 的 `initial_messages` 注入），
   重写一遍会引入分叉风险；复用它是"接缝稳定"的证据。
4. **把工具沙箱/审批也在 `_05` 重做一遍**。排除：`_03` 的管线与 `write_file` 沙箱
   已经齐备，`workspace_tools.py` 只需按新工作区重新绑实现即可；重做 = 无意义重复。

## 后果

- 约束：`_05` 不得修改任何被组装的包（只能接线 + 提供工具面）；不引入新抽象层。
- 收益：组装几乎零机制成本——`MiniHarness` 约 130 行、`app.py` 是 CLI 外壳；
  13 个测试全离线、0.18 秒；真实 API 实测走通 `calculate → write_file → 回答` 三步链，
  跨进程 resume 后 turn 接续并成功读回上一轮写的文件。
- 债务：各练习的同名包副本重复存在，全量测试依赖 `conftest.py` 驱逐模块；
  M4 起收敛正式包结构时一并解决。
- 后续：M4–M7 在 `harness/` 正式包上继续（提示词装配、能力接缝、profile、服务化）。
  `_05` 的 `MiniHarness` 是那条主线的"接线范式"样板。

## 附：一处刻意的范围收缩

`_05` 的工具面包含文件读写（带沙箱 + 审批）与可选搜索，但**不含 shell / subprocess**。
原因是 shell 的隔离需要真正的子进程能力（M5 的 `SubprocessService` 与 M8.3 的沙箱），
在应用层用 `subprocess` 裸跑会给出虚假的安全感。宁可工具面小一点，也不引入一个
"看似有沙箱、实则可逃逸"的 shell。这与铁律 #8（fail loud）和"宁可任务没做完，
也不默认放行危险操作"的取向一致。
