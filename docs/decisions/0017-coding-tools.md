# 0017 编码工具三件：能力面补齐在既有接缝上，不引入新机制

- 日期：2026-10-09
- 阶段：P2_Coding/_11_Session_Follow（学习计划 M7，与 follow 同阶段）
- 状态：已采纳

## 背景

P2 走到最后，工具面一直是 `_04`–`_06` 留下的那几件：`calculate`、`read_file`、
`write_file`、`list_files`、`shell`。它能"跑起来"，但**离一个基本可用的 coding
agent 还差三件最常用的事**：

1. **改一行**：`write_file` 是整文件重写——模型改一个词要把整个文件重发一遍，
   既费 token 又容易手滑改坏其它行；
2. **找代码**：`list_files` 只给文件名，模型要看内容得逐个 `read_file`；
3. **按名找文件**：大目录里定位 `test_*.py`、`*.md` 得靠 `shell`（Windows 上还
   有编码问题），而"按名查找"本是纯文件能力、不该绕道命令执行。

## 决策

**1) 只加"能力"，不加新接缝**：三个工具全部骑在 `_04` 的 FileSystem 协议上
（edit_text / list_files / read_text）——于是它们在 local / memory / jail 下
**行为一致**，且**策略自动生效**：jail 围栏对 `edit_file` 照拦（越界改动被拒），
而 `search_text` / `find_files` 是只读的、不受围栏影响（策略只拦改动，0010 的边界）。
若绕开接缝直接碰 pathlib，这三个性质全部要重新实现一遍。

**2) `edit_file` 的语义直接从接缝拿**：`old` 必须恰好出现一次才替换；0 次报
`FS_EDIT_NO_MATCH`、多次报 `FS_EDIT_AMBIGUOUS`（拒绝猜）。这套语义是 `_04` 定
`edit_text` 时就设计好的（当时已预判"改文件比写文件更容易出错"），本阶段只是
把它暴露成工具。**"拒绝歧义"是编码代理最重要的防误改机制**：模型想改的是
"第 3 行那个 `i`"，而不是"文件里所有 `i`"——歧义时宁可报错让它给更精确的原文。

**3) 检索有上限、截断如实说**：`search_text` / `find_files` 的 `max_results`
（默认 50 / 200）防一次大搜索把工具结果和会话日志炸掉；截断时在结果里带
`truncated` 说明和"请收窄条件"的提示——**错误/截断都是给模型的输入**（铁律 #7），
它据此自己收敛查询，而不是拿到一个静默裁剪的假结果。

**4) 坏输入结构化返回**：坏正则报 `{"code": "INVALID_PATTERN"}`、路径问题走既有
`FsError` 翻译——与其它工具错误同形（`{error, code}` 两键），调用方/模型用同一套
处理逻辑。

**5) `edit_file` 与 `write_file` 同级审批**（`needs_approval=True`）：改文件与写文件
同样是有副作用的动作；`search_text` / `find_files` 只读、不需要审批。

## 备选与排除理由

1. **`edit_file` 用"替换全部出现"语义**。排除：那正是模型最常犯的错（改掉整个
   文件的同名变量）；"恰好一次"逼调用方提供带上下文的精确原文，是更安全的默认。
   要改多处就多次调用——每次都是可审计的明确改动。
2. **检索工具绕开 FileSystem 用 pathlib**。排除：memory/jail 下失效，且策略
   （越界/围栏）要重写一遍。接缝的意义就是"工具只认协议"。
3. **`search_text` 不设上限（返回全部）**。排除：一次 `pattern="."` 就能把几 MB
   文本灌进会话日志；上限 + 如实截断是保住日志与上下文的基本防护。
4. **给 `edit_file` 加"行号定位"参数**。排除：行号会漂移（多步编辑后），而"原文
   匹配"是内容寻址、自校验——`old` 找不到就是文件变了，模型正好知道要重读。
5. **把 `shell` 当万能工具、不加新工具**。排除：跨平台（Windows 编码/命令差异）、
   越权面（shell 需审批且能执行任意命令）、结果解析都更糟；"读、搜、改"是高频刚需，
   值得一等公民工具。

## 后果

- 约束：三个工具都不得越过 FileSystem 协议（新增文件能力的正确姿势是扩展接缝，
  不是加 pathlib 调用）；`search_text` 的 pattern 是正则（区分大小写），
  对非文本文件按"读失败则跳过"处理（不炸整个检索）。
- 收益：**真实 API 实跑验证**——"找出所有 TODO 并改掉 helper.py 里那个"：
  模型 search 找到 2 处、edit 只改要求的那一个、另一处主动留下并说明，
  磁盘文件确认被正确修改（app.py 未动）。三工具各有测试覆盖 local/memory/jail
  与三类失败（no_match / ambiguous / bad_pattern / 截断）。
- 债务与后续：
  1. **search 无 regex 之外的选项**（大小写不敏感、glob 过滤等）；需要时加参数。
  2. **无"读文件片段"（offset/limit）**：大文件仍靠 `shell` 的 `head`/`tail`
     或整读；对真正的大仓库，带窗口的 read 是下一个该补的工具。
  3. **web_search 的可选项保持原样**（需网络，默认关）。
