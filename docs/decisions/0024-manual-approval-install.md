# 0024 手动审批 + 从工作区安装插件（浏览器里看代码批准）

- 日期：2026-10-14
- 阶段：P3_Coding `_01_Self_Plugin_Tools`（决策 0023 的扩展）
- 状态：已采纳

## 背景

决策 0023 立下"可装载 = 白名单里的名字"这条边界，明确排除了"从磁盘/工作区
加载任意代码"——理由是那等于把任意代码执行权交给模型。但用户随后提出了一个
真实的测试需求：**要验证"实时编写插件并安装"的能力**，即模型写一个新插件、
人看过之后决定装不装。

这要求 0023 的那条线**往前挪一步**：从"只有预先批准的名字"变成
"新代码可以进，但必须每次有人当场点头，且人能看见代码"。

同时暴露了 0023 的一个空缺：`--web` 场景下审批没有落点。原来的策略只有
终端 y/n（`PromptApprover`）与自动放行/拒绝；网页里既没有终端可问、自动放行
又等于没审。实测表现为 `shell`/`write_file` 直接返回"非交互终端：无人可审批"。

## 决策

**1) 新增 `plugins/web_approval.py`：把"问人"搬到浏览器。**

    WebApprovalPolicy —— ApprovalPolicy 的实现
      推 __approval 帧（工具名 / 参数 / 原因 / 源码预览）→ 阻塞等
      POST /api/approvals/<id> → 无连接或超时（默认 300 秒）一律 fail-closed

`AgentService` 打开会话时解析策略的顺序改为：**显式传入的优先，否则用 ctx 里的
`approval` 服务**，都没有则 None（管线按 fail-closed 拒绝）。于是
`chat.py --web --self-tools` 默认就是"浏览器里点批准"。

**2) 新增 `install_plugin` 工具：唯一能引入新代码的入口。**

    install_plugin(path)  工作区里的 .py → 读源码 → **人工审批** → 装载 → 入白名单

三条硬约束：只接受 `.py`；只读工作区内的文件（走 `fs` 服务，天然受沙箱限制）；
审批被拒则**什么都不发生**（不留白名单登记、不动工具面）。装载失败会**回滚**
刚做的白名单登记（`test_install_plugin_rolls_back_whitelist_on_load_failure`）。

**3) 审批在两层都成立（不依赖调用方记得走管线）。**

工具带 `needs_approval=True`（管线 pre 阶段拦一次）；服务层的 `install()`
**自己也问一次**——因为公共方法可能被直接调用（测试、未来的别的入口），
"引入新代码"太敏感，不能只靠"记得走管线"。为避免重复弹窗，工具包装器用
**线程局部标记**（`_approved_call`）声明"管线已批准过"，服务据此跳过第二次。

**4) 白名单从"只读"变成"经审批可增长"。**

`SelfToolsService.register_factory` / `make_unloadable` 是写入端，**只由审批路径
调用**。`install` 成功后，新插件同时进入可装载与可卸载白名单——用户批准过的
东西，也允许模型自己卸载（同样是审批动作）。

## 备选与排除理由

1. **不做 install，只让模型"建议"装什么**。排除：那就回到 0023 的形态，
   无法验证"实时编写 + 安装"这条链路。
2. **审批不阻塞、异步放行**（先返回 pending，之后回调继续）。排除：工具调用
   的语义就是"执行完给结果"，异步会让 turn 的状态机复杂一大截；阻塞等待
   （带超时）对单会话场景足够，且"超时即拒绝"天然安全。
3. **审批走终端问**。排除：网页场景没有终端；而"网页里点批准"本身就是要验的
   交互。
4. **install 不再设白名单，装完即可卸**。排除：那等于一次批准换来永久权限。
   当前设计是"批准 = 这一次装载"，卸载也需要重新批准——更保守。

## 后果

- **收益**：完整链路打通并实测——模型写 `plugins/dice.py` → 弹审批（**看得到
  源码**）→ 批准 → `dice` 出现在插件台账、`roll_dice` 进入工具面。左栏台账
  会高亮新增插件（`plug-new` 动画 + 绿点），刷新间隔缩到 2.5 秒。
- **约束与已知边界**：
  1. **审批超时默认 300 秒**，超时按拒绝（可配）；等待期间占用会话锁
     （同一会话的其它请求排队）。
  2. **只接受工作区内路径**（`fs` 服务限制）；跨目录读源码需要更宽的 fs 权限，
     不在本阶段范围。
  3. **装载的代码以完整进程权限运行**——不是沙箱。安全边界只有"人看过代码并
     批准"。这是本阶段刻意的取舍（对齐 dsh 的 `tool-cordis` 有沙箱、我们靠审批）。
  4. **白名单只活在内存**：进程重启后 install 的插件消失（与"每次启动重新装配"
     一致）；文件还在工作区，可再次安装。
- **债务与后续**：
  1. 审批的**审计痕迹**目前是 `approval/requested`、`approval/resolved` 事件 +
     工具调用进日志；尚无专门的"审批历史"查询视图。
  2. `install` 的预览固定展示源码前 2000 字符（够看，但长文件会截断）。
  3. 未来若要"沙箱化装载"，应走子进程/受限解释器，而不是继续放宽这里的边界。

期间修掉一个真 bug（已加回归测试）：审批推流的 attach/detach 没有作用域，
先结束的 turn 会把后来者的通道清掉，导致审批误报"浏览器未连接"——现在
`detach_stream(handle)` 带句柄、只摘自己挂的那个，且挂/摘都移进了会话锁内。
