# 0035 角色由装配方定：`base` / `capability` 是应用的性质

- 日期：2026-10-15
- 阶段：P3_Coding `_05_Compaction`（收尾）
- 状态：已采纳

## 背景

用户问："为什么 webui 是能力插件不是基础插件？"

我的第一版回答是"因为卸了它应用照样成立"——标准装配不装它，agent 照跑。
这个理由解释了**默认组合**，但用户接着指出一个我漏掉的情形：

> 对于 webui 的应用组装发布而言，webui 插件就应该是基础插件而不是能力插件

他说得对。`python chat.py --web` 启动的东西**就是那个网页**——用户拿到的产品
形态没有别的东西：没有页面就没有入口，"这个应用"不成立。在这种组合里 webui 是
地基，不是可选能力。

而当时的机制**做不到这个区分**：`category` 只能由插件自己声明
（`plugins/webui.py` 里写死 `category = "capability"`），装配方没有话语权。

### 后果不是"标签贴错了"，是一个可复现的自断路径

界面即产品的组合里，webui 卡片带着"停用/卸载"按钮。实测（在页面上点"停用 webui"）：

1. 请求返回 200，弹出回执"已停用 webui"（响应在端口关闭前发出）；
2. 端口**停止监听**，新连接进不来（`curl` 得到 `000`）；
3. 但当前标签页那条 keep-alive 连接仍是 `ESTABLISHED`，**页面还能刷出来**，
   显示"11/12 活跃"；
4. 于是只有"当前这个标签页还开着"时才能自愈（点那条老连接上的"启用"）。
   一旦关掉标签页，**只能回终端**把它装回来。

**用页面把承载页面的插件关掉**——这正是"发布一个界面应用"时最不该出现的按钮。

## 决定

### ① 判断权归装配方：`load_plugin(role=...)` / `boot(roles=...)`

```python
ctx.load_plugin(webui_plugin(port=0), role="base")          # 单个
boot(plugins=[...], workspace=..., roles={"webui": "base"}) # 整批
```

插件自己的 `category` 降级为**默认值（推荐角色）**，不再是最终裁决。
新的 `kernel/plugin.resolve_category(plugin, role)` 做这件事：
装配方给了就用它，没给才读插件自述。

**为什么内核要多这个参数**：`base` 的定义是"卸了应用不成立"——这句话的主语是
**应用**，不是插件。同一个 webui：

| 装配 | 应用形态 | 卸了它还成立吗 | 角色 |
|---|---|---|---|
| `chat.py`（终端 REPL）、`--rpc` | 命令行应用 | 成立（终端/RPC 也能说话） | capability |
| `chat.py --web` | **界面即产品** | **不成立**（没有页面就没有入口） | base |

**两个装配、两种角色**——所以声明权必须在装配方手里，这是本决策的核心。

### ② 入口按自己的形态接线

```python
# chat.py
INTERFACE_ROLE = "base"                       # 「界面即产品」的角色

def start_webui(booted, *, port, role=None):  # 装载时把角色交给内核
    booted.ctx.load_plugin(webui_plugin(port=port), role=role)

def serve_web(...):                           # --web：就是那个网页
    url = start_webui(booted, port=port, role=INTERFACE_ROLE)

# REPL 里的 /web：不传 role —— 在终端应用上临时开的观察窗口，关掉照常用
```

`plugins/boot.py` 同时提供 `INTERFACE_ROLES = {"webui": "base"}`，供别的
"界面优先"组合直接复用。

### ③ 非法角色照旧 fail loud

`role` 写错一个字母（`"basel"`）会在**装载期**报错，而不是悄悄降级成默认角色——
理由同 `plugin_category`：静默降级会让一个地基插件突然变成可卸载的。

### ④ 运行时装载不传角色

模型自扩展（`load_plugin` 工具）、面板里点"安装"都**不传** `role`——那不是
"装配应用"，没有装配方的立场，用插件自述即可。所以同一个 webui 在
"界面应用里是地基、被模型临时装进终端应用时是能力"是合理的。

## 代价

- **多了一个可以传错的参数**：装配方声明错了，界面就显示错。缓解：非法值
  fail loud；测试钉住"两条入口各自声明什么"。
- **概念上多了一层**：读代码时要问"这个应用里它是什么角色"，而不是"这个插件
  是什么角色"。代价换来的是"发布一个界面应用时，界面不会被自己关掉"。
- **`role` 只在装载期生效**：装载后再传不进去（台账记录里有 `category` 快照）。
  要改角色只能重装——这与"角色是装配决定"的语义一致。

## 实测

- **同一个 webui，两种装配两种策略**（直连内核验证）：

  | 装配 | 分类 | 台账按钮 | 停用尝试 |
  |---|---|---|---|
  | 不传 role（终端） | capability | 停用 · 卸载 | `已停用 webui` |
  | `role="base"` | base | （无按钮） | `不能停用 webui：基础插件是当前应用的最小集合` |

- **真起 `--web` 服务**：`GET /api/plugins` 里 webui 落在 `base` 组、`actions: []`；
  页面上它出现在"基础插件 8"里，带"不可卸载"标记、**没有按钮**。
