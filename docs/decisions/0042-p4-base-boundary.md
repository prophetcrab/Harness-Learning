# 0042 P4 基座边界：支持「harness everything is plugins」的最小底座

- 日期：2026-10-16
- 阶段：P4_Coding（目标已定，未开工；本记录定基座边界）
- 状态：已采纳（M1 按此边界完成；2026-10-19 补记：动态 `ctx.inject` 已落地、插件级 `requires` 已加入）

## 背景

用户对 P4 基座的定位（三轮讨论收敛）：

> 基座 = 支持 harness **everything is plugins** 的**最小**底座：提供
> 插件树管理、按装配单装配、热插拔三件事；harness 的一切能力只以插件形式存在。

这句话要能验收，先把它转成**可检查的判据**（否则「最小」只是感觉）：

1. **除基座外没有非插件部分**——harness 的每份能力都在树上占一个条目，
   卸掉条目就是卸掉能力；
2. **装卸不动别人**——插件之间只有两条通道：服务（协作）与事件（观察/拦截）；
3. **基座自足且不懂 harness**——空装配单能起；基座源码里不出现任何 harness
   词汇（llm / tool / session / agent / prompt / web …），用测试扫词钉住。

## 决策

### 非插件只有 core 一处：框架（物理定律）+ 引导（自带启动器）

> **状态（2026-10-16）**：M1 八步全部落地、165 用例全绿——本表已由代码与
> 纯度测试（`tests/test_purity.py` 的三级扫描）钉住。

| 层 | 角色 | 内容 |
|---|---|---|
| **core · 框架**（非插件） | 插件世界的「物理定律」 | 服务槽位（provide / require / get）、事件（emit / waterfall）、effect 回卷、**单插件**生命周期（load / unload / disable / enable + 依赖驱动的 settle 稳定化）、一把可重入变更锁、快照原语 |
| **loader**（插件） | 插件世界的「行政系统」，**自己也是插件** | 条目（id / name / config / role / enabled / children）、树与路径寻址（`a:b`）、按装配单装配、名字解析与 config 注入、热插拔（load / unload / disable / enable / update / replace 按 id 原子操作）、revision 与树快照、变更报告（谁连带退位 / 谁重新激活） |
| **core · 引导**（非插件；`core/launcher.py`，步 8 长出） | **自带启动器**：拿到 core 就能起一个装配 | 读装配单 → 挂上 loader（唯一的特权步骤）→ 产品政策检查（角色词表、「至少一个应用化插件」；**只在"起产品"时执行**，裸装配照起）→ `--dump` 报告 |

**为什么启动器收在 core 里**（2026-10-16 定）：基座应当**自带启动器**——
`boot(装配单路径) -> 运行时`，空装配单也能起（这就是判据 3「基座自足」的
落点），不需要外部胶水；非插件部分由此只有 **core 一处**。

**harness 的一切能力都在树上**；代码里不在树上的只有 core，两个角色、两级纪律：

- **框架模块**：先于插件存在（它不能是自己的插件）；**不认识任何插件**，
  一律不 import plugins；不出现任何 harness 词汇；
- **引导模块**：唯一的**组合根**（composition root）——「先有鸡才能装鸡」，
  loader 由它直接挂上（不由 loader 自己装载自己），此后每条条目都经
  `loader` 服务装载；它认识 loader 一个插件（函数内懒加载，全仓唯一的向上边）。
  启动器做的是**引导**，不是能力：`cli` / `web` / `sdk` 这些产品形态都是插件，
  读哪份单子、把 loader 点着这一步才是它的活；
- **词汇纪律分两级**：harness 词汇（llm / tool / session / agent / prompt /
  web …）在 core 里一律禁；三类角色词表（base / application / capability）
  是 **P4 自己的产品概念**（0041），允许出现在引导、禁止出现在框架模块——
  纯度测试按这两级来扫（步 8）。

**与 dsh 的差异（如实）**：dsh 把引导放在独立包（`app-boot` + `apps/cli`），
因为它要处理 profile / `.env` / patch 分层；我们的引导不做这些（装配单就是
一份数据），规模小到收进 core 更清楚。将来真需要多个产品入口，把
`core/launcher.py` 整体搬出去即可（一个文件搬家，改几行 import）。

三条补充规则：

1. **loader 为什么是插件**：dsh 里 `ctx.plugin` 在核心（单插件）、加载器
   `@cordisjs/plugin-loader` 是插件（条目树、`ctx.loader.create/update/remove`）。
   我们照此分。好处有两层——「装配」本身可替换（换装配单来源 = 换 loader 实现，
   核心不动）；管理面插件、模型管理工具与启动器走**同一条服务通道**（`loader`
   服务），没有内部 API 直呼。**停用 loader 后已装配的树继续运行**（只是不能再
   变）——这是「装配不是特权」的可测形式。
2. **树的父子与所有权级联是 loader 的记账**（卸父先卸子、深的先退；
   disable / enable 以子树为单位）；**不引入服务作用域隔离**——服务是单一命名
   空间，同名槽重复提供 fail loud。core 台账按**插件名**记账：一个运行时里
   一个插件名只留一份实例；同插件多实例（如两台 web）**暂不支持**——需要时
   再把记录改成按句柄寻址（触发条件：出现第一个真需要多实例的插件；届时
   loader 装配期应就此给出清晰报错）。
3. **role 是搬运的数据，不是基座的知识**：基座只存 role 字符串；
   `base / application / capability` 这套词表与「至少一个应用化插件」的断言属于
   产品政策，在启动器执行。

### core · 框架的职责清单（六件 + 一个补丁；2026-10-16 收束）

| # | 职责 | 关键语义（验收钉的点） |
|---|---|---|
| 1 | **服务槽位** | provide / get / require / retract；重名与缺失 fail loud；拒绝原子（原值不被动）；没有 set——换实现是显式 retract + provide ✅ 已绿（M1 步 1） |
| 2 | **事件总线** | `on`（返回退订）/ `emit`（广播，注册序）/ `waterfall`（中间件链：`handler(value, **ctx)` 返回非 None 即替换）；handler 抛错 fail loud（吞错是消费方的策略，不是总线的）；装载期订阅随 effect 回卷 |
| 3 | **effect 回卷** | `ctx.effect(install)`：装载期一切登记（服务、订阅、嵌套 effect、插件自己的资源）自动撤销；回卷"子先父后、同级后进先出"；一个 disposer 抛错不打断其余（最后重抛第一个）；装载失败不留半装 |
| 4 | **单插件生命周期** | 插件协议（name / inject / optional / **requires** / setup）；状态 pending / active / disabled / failed；settle 稳定化——依赖齐自动激活、提供者走了自动退位、**装载顺序无关**；load / unload / disable / enable；退位顺序"深的先退"（依赖者清理期间服务仍可用）；台账快照（missing / missing_optionals / missing_requires / error）✅ |
| 5 | **变更串行化** | 一把可重入变更锁：所有改变世界的操作串行；**重入合法**（插件在 setup / dispose 里装卸别的插件）**且嵌套并入最外层**（一次用户动作 = 一个 revision）；每次有效变更 revision + 1（用前后签名判定——报错但世界确实变了也 +1，彻底回滚的失败不加）✅ |
| 6 | **快照原语** | services / plugins / effects / revision / `last_change`（谁退位、谁激活）——loader、管理面、测试、启动器共用同一个读取面 ✅ |

（引导 / 启动器不在这张表：它是组合根，不是机制——见上表「core · 引导」一行。）

**第 7 件（2026-10-16 补）：动态依赖 `ctx.inject(deps, callback)`**——与静态
`inject` 是一对，解决"注册型副作用"：插件主体照常跑，**这一块**等依赖齐了才
运行；依赖走了自动拆（回调的登记挂在子 effect 下）、回来重跑。`optional` 表达
不了它（"来了不重装"），静态 inject 也表达不了（会拖住整个插件）。dsh 里 57 处
用法全是这个形状（挂拦截器、加提示词段、注册变量）。订阅本身在装载期注册时
随外层 effect 回卷；回调抛错标 failed、**不原地重试**（依赖变化后才重试）。

**为什么事件必须是第二件"实权"机制**（dsh 实证）：72 个 harness 事件全走总线，且在
主路径上——`agent/pre-step` 有 14 个消费者、工具管线四段 `tools/*-execute` 全是
waterfall、连 `llm/stream` 也是 waterfall。**循环不"调用"插件，而是发事件、插件挂上去**。
所以 waterfall 的中间件语义就是**策略插座**的本体：P4 要闭的第三处差距（guard 插件）
挂在这里。

**一条边界提醒**：事件总线 ≠ 会话日志。总线管"此刻投递"，日志管"永远记住"——日志是
一条订阅总线的能力插件（dsh 的 `session-persistence-jsonl` 就是这个形状），不是 core。

**句柄语义（2026-10-16 补，实测教训）**：装载返回的卸载句柄**认"这一次装载"**，
不是认名字——重复调用、对应对象已随父回卷、已被同名新对象顶替，都是**安全空操作**；
而按名字的 API（`unload_effect` / `unload_plugin`）保持**严格 fail loud**。分工是
刻意的：句柄出现在清理顺序不确定的场景（`ctx.effect("p", lambda: ctx.effect("c", ...))`
这种自然写法会返回子句柄），名字出现在人手敲的地方（敲错必须立刻知道）。
另：install 的返回值若是账本里已有的函数（如 `lambda: ctx.on(...)`——`on` 返回的
退订函数早已自动登记），不重复记账。

### 明确不属于基座（「最小」的删减清单）

| 移出 / 不做 | 去处 / 理由 |
|---|---|
| 角色词表校验、「至少一个应用化插件」检查 | core · 引导（启动器；产品政策——换一个产品可以有别的词表） |
| 稳定态审计 `verify()` | 做成诊断能力插件（先例：dsh 的运行时诊断 invariants 是插件，标准组合刻意不挂它）；基座只用构造保证（settle 到稳定态 + effect 嵌套回卷）+ snapshot 供外部检查 |
| **日志服务** | 不进 core：dsh 里 `ctx.logger` 用量很大（142 个文件），是因为 TS 侧没有环境自带的日志设施；Python 有 stdlib `logging`，插件直接用它就是"谁都有的日志"。触发条件：需要**可替换的日志**（如把日志送进网页）时，做成一条订阅事件总线的能力插件 |
| 定时器 / HMR / 配置 schema 框架 / 变更事件 | 不做或后置：各自等真实使用者（dsh 里 timer、HMR 是独立可选包；isolate / intercept / check 在 dsh 使用 0 次） |
| `parallel` / `serial` / `bail` 分发模式 | 不加：dsh 72 个事件里 parallel 3、serial 2、bail 0；真要加是**新增方法**，不改已有 API |
| ~~动态 `inject(deps, cb)`~~ | **已补（2026-10-16）**：`ctx.inject(deps, callback)` 进 core——依赖齐了跑一块、走了自动拆、回来重跑；回调的登记挂在子 effect 下，订阅在装载期注册时随外层 effect 回卷。理由：dsh 用了 57 处，且它解决的是 `optional`（来了不重装）与静态 inject（整插件等依赖）都表达不了的"注册型副作用" |

### 两条立场（沿前轮讨论）

1. **运行时变更不回写装配单**：装配单是只读真相，页面 / 模型在本次进程内的
   开关重启即回；「记住开关」留给 M5 决定（届时用单独的 user overlay 文件）；
2. **id 即路径，不做移动**：改位置 = 改装配单重装子树；配置整份给、不做字段
   合并；配置里的相对路径以**装配单所在目录**为基准。

## 验收（机器可查；M1 的测试基线）

1. **基座纯度**：空装配单能起（基座自足）；基座源码无 harness 词汇、不 import
   harness 模块（词表扫描 + 依赖方向测试，命中即红）；
2. **最小装配**（三个假插件）：打乱装载顺序结果一致；卸根节点整棵消失，服务、
   订阅、登记物一个不剩；依赖来去自动激活 / 退位；快照可读；
3. **能力 = 条目**：从装配单删掉某能力 → 产品照起、该能力恰好消失；加回 → 回来；
4. **热插拔原子**：update 造新失败 → 旧的原样、服务不断档；运行中换 llm →
   新会话用新的、已打开的会话不受影响；
5. **loader 可停用**：停用 loader 后树继续工作，只是不能再变；
6. **插件间无 import**：跨插件只有服务名与事件名两种约定。

## 备选与排除理由

- **A. 装配功能（条目 / 树 / 热插拔）也放进核心**：否决——「按装配单装配」就成
  不了可替换能力，「everything is plugins」在同一份代码里破例；管理面只能直呼
  核心内部 API。代价是启动器多一步引导（唯一特权步骤），值得。
- **B. 现在就做分层 patch / 热重载 / 作用域隔离 / 配置 schema**：否决——dsh 里
  isolate / intercept / check 使用 0 次、HMR 默认关；都是「有真实使用者再加」
  的类型（触发条件后置到需要时）。

## 代价（如实记下）

- loader 是插件带来一次引导特权：启动器必须「第一个装 loader」——全仓唯一一处
  「代码知道怎么启动」（dsh 同构，不是缺陷）；
- 核心与 loader 全部从零写（不搬 P3 代码——见[决策 0043](0043-p4-rewrite-from-scratch.md)）；
  边界由此更干净：核心天生只含框架机制，条目 / 树 / 装配单 / 热插拔一开始就在
  loader 里；
- 稳定态审计后置：装完「看着好了、实际留了半个」的问题先靠测试兜（验收 2 的
  「一个不剩」就是它），真疼了再加诊断插件。
