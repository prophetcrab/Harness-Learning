# 0039 用户报告的三处修复：端口争抢、面板闪烁、被截断的日志

- 日期：2026-10-16
- 阶段：P3_Coding `_06_Tool_Plugins`（修复另有回填到 `_05` 与基线）
- 状态：已采纳

## 背景

用户报告两件事：**"token 用量和上下文不随着使用更新了"**、**"插件和工具的管理面板
一直在闪烁"**。查下去发现是三个独立的问题，其中第三个的成因还牵出一处更早就埋下的
健壮性缺口。

## 一、徽标不更新：固定端口被多个 harness **静默争抢**

`token-usage`（8767）与 `context-meter`（8768）用固定端口，是为了给人一个记得住的
入口。但本机同时跑着三个 harness（页面上分别是 8783 / 8070 / 8795），三个进程都会
去 bind 同样的端口：

| 平台 | 第二个 bind 的行为 |
|---|---|
| Linux | `EADDRINUSE` 抛错——吵，但看得见（插件装载失败） |
| **Windows** | Python 的 `HTTPServer` 默认 `allow_reuse_address = 1`，**不报错**——两个 socket 同时 LISTENING |

于是每个进程都以为"我的账本在 8767"，而客户端连到哪一个**由内核决定**。
用户页面上看到的就是：聊了半天，`Token` 与`上下文` 纹丝不动（读的是另一个进程的账本）。

**修法**（`components/net.py` 的 `pick_port`）：bind 之前先探一下端口有没有主
（一次本机 connect），有主就交回 `0` 让系统分配，并**如实公布实际端口**
（两个插件本来就用 `server.server_address[1]` 填服务地址，所以公布值不会骗人）。
第一个进程仍然守着固定端口当"人记的那个入口"，只是拒绝**静默争抢**。

**为什么不干脆都改成随机端口**：固定端口的价值就是"人记得住、能直接在浏览器敲"。
保留它给第一个进程，代价只是"第二个以后要用自己页面上的链接"。

## 二、管理面板一直闪：指纹"两边各写一份"，永远不相等

`_06` 的重画节流是这么写的：

    renderAdminPanel:  adminPanel.stamp = JSON.stringify({tab, s, a})
    loadLedger:        比较 JSON.stringify({tab, p, s, a})   ← 多一个字段

两个字符串**永远不会相等**，于是"内容没变就不重画"的判断永远失效：每 2.5 秒重写
一次 `innerHTML`，卡片带着入场动画（`.pm-card{animation:pm-in}`）反复重播——
看起来就是面板一直在闪。

**修法**：指纹只由**一处**计算（`adminStamp()`），渲染与比较都用它。要加字段就改
那一个函数，两边自动一致。另外顺手修了同类的一处：顶栏按钮原先每 2.5 秒
`innerHTML = ""` 重建一次（按钮先消失再出现），改成"自述没变就不重建"。

**一般化的教训**：节流判断的"指纹"必须在**渲染方与比较方之间唯一**。两份长得像
的表达式就是两个不同的东西——而这个项目已经反复栽在"两处需要记住同步"上
（决策 0031 / 0038 同一主题，这次是它在前端的版本）。

## 三、会话永久 400：被截断的日志投影出**孤儿工具结果**

现场：某会话每轮请求都失败，页面只有一行
`Error code: 400 - Messages with role 'tool' must be a response to a preceding
message with 'tool_calls'`——**这条会话再也发不出任何请求**，用户完全不知道该怎么办。

成因：会话日志**头部被截**（文件被外部改动/清理过），投影出的第一条消息变成某个
工具结果，而它对应的 `assistant(tool_calls)` 已经不在了。另一种同源形状是
"进程在结果落盘前被杀"：`assistant` 声明了调用，但没有任何结果。

两种形状都会被 API 拒绝（这就是 P0 记下的协议约束："漏掉任何一边，模型下一轮就会
失忆"——这里是更硬的失败：请求根本发不出去）。

**修法**（`projection.sanitize_pairs`）：投影的最后一步做**只删不造**的修剪——

    孤儿工具结果        → 丢掉（对应的申请不在投影里）
    没人应答的 tool_call → 从 assistant 消息里摘掉（摘空且无正文则整条丢）

**为什么是"删"而不是"补一条结果"**：补 = 往模型历史里塞进日志里没有的内容，
违反铁律 #1（模型可见即已记录）。删只影响投影（日志一个字节不动），而且"发生过
什么"仍能从日志里查（`assistant/message` 的 tool_calls 还在）。重放仍然同构：
每次重放做同样的修剪，结果一致。

**影响面**：不只"被人工清理"这一种场景——**崩溃/断电在结果落盘前**也会留下第二种
形状；日志被同步工具改过、磁盘写坏一行同理。所以这条修复不只服务于这一次的现场。

## 代价与边界

- `pick_port` 的探测是**尽力而为**：探完到 bind 之间仍有理论竞态窗口（本机练习
  场景可忽略；真要在意就得上"bind 失败重试"的循环，那是另一个决定）；
- 修剪是**不可逆地改变了模型看到的历史**（相对日志）。这是刻意的取舍：一份能被
  API 接受、能继续对话的历史，好过一份"忠实但与日志同归于尽"的历史。**日志仍
  是真相**——诊断时读日志，模型历史只是它的视图；
- 修剪只在**配对不上**时生效：正常日志一条不动（有测试钉住）。
