# 0032 壳的两条扩展点：显示自述与路由自述（界面零知识）

- 日期：2026-10-15
- 阶段：P3_Coding `_05_Compaction`（收尾；用户要求"不要过于耦合"）
- 状态：已采纳

## 背景

用户问"架构符合完全插件的原预期吗"，实测后的结论是：**主体符合，但界面还差两层**。

- 面板已经零知识了（`_05` 收尾的第一批修复：插件自述、壳遍历）；
- 但**"事件怎么画"与"插件专属端点"仍然写死在壳里**：

```js
// app.js —— 认得出具体业务词汇
case "compact_applied": ...   case "compact/checkpoint": ...
case "compact_failed":  ...   case "__compact_done": ...
const TERMINAL_FRAMES = new Set([..., "__compact_done", "__compact_noop"]);
```

```python
# webui.py —— 为具体能力写死的路由
POST /api/sessions/<id>/compact    # 压缩插件的
GET|POST /api/approvals[/<id>]     # 审批插件的
```

数一下：改造前 `plugins/webui.py` 提到 compact 10 处、`app.js` 17 处。
**结论**：加一个需要端点或需要特殊渲染的插件，**必须改壳**——"完全插件化"
在展示层是假的。

## 决策

**1) 新增 `components/shell/` 契约层，统管三类自述。**

| 文件 | 自述 | 回答什么 |
|---|---|---|
| `panel.py` | `PanelSpec` | 我有个页面 → 给我一个按钮 |
| `display.py` | `DisplaySpec` | 我的事件该怎么画 |
| `routes.py` | `RouteSpec` | 我有专属端点 |
| `discover.py` | `panels_of/display_of/routes_of` + `Surface` | 统一发现 |

`Surface` 是自述载体：当服务对象是 `components` 层的类（如 `Compactor`）时，
插件另 provide 一个 Surface 即可，**不必为界面契约去改别人的类**。

**2) `DisplaySpec` 只认四种通用渲染器**（`fold` 可折叠徽标 / `note` 一行小字 /
`warn` 黄条 / `status` 只更新状态栏）。

- **为什么是固定的四种**：壳不该长成一个模板引擎。四种覆盖了"事件该怎么显示"
  的全部常规形态；真需要特殊呈现的（图表之类），那是插件**自己的页面**该做的事
  ——它已经在面板里挂了一个 iframe。
- **模板只有"取字段"**：`"折叠 {folded} 条"`，壳负责数字格式化与缺值兜底。
- **`terminal: true` 标记"这是流的收尾"**：前端把壳内置的 `__done`/`__error`
  与插件自述的 terminal 帧合并成收尾帧集——不再写死 `__compact_done`。

**3) `RouteSpec` 让插件**完全不碰 HTTP**。**

```python
def handler(request: RouteRequest) -> None:
    outcome = request.ctx.get(AGENT_SERVICE).compact(request.params["id"])
    request.stream().frame("__compact_done", {...})
```

handler 拿到的是：解析好的路径参数、解析好的 JSON 体、以及一个 `stream()`
帧写入端。**分块传输、CRLF 分帧、终止块全归壳**——那几处最容易写错
（本项目实测踩过三次：HTTP/1.0 导致"逐字"退化、漏写终止块让客户端挂住、
双重编码导致客户端超时），集中一处只写一遍。

**4) 路由表每次请求现建，不缓存。**

自扩展工具能在运行时装卸插件，缓存会让新插件的端点装不上、卸载的插件端点还留着。
与"服务一律现取"是同一条纪律。建表很便宜（遍历几十个服务读个属性）。

**5) 审批卡片保留专门处理——有意的边界。**

`__approval` 不走 display 自述：它是**交互**（要按钮、要回传答案），
不是**展示**。display 的职责边界就是"把一条事实画出来"；带交互的组件由插件
自己的页面（面板 iframe）承担。混在一起会让"通用渲染器"变成一个要处理
事件绑定、状态机的框架——那正是本决策要避免的方向。

## 备选与排除

1. **让壳认更多事件名**（继续 case-by-case 加分支）。排除：这正是要解决的问题
   ——每加一个插件都得改壳。
2. **把渲染做成插件提供的 JS 代码，壳 eval 执行**。排除：等于让插件往壳里
   注入代码，安全边界没了（这个壳是给模型装卸插件用的）。
3. **让 handler 直接拿 `BaseHTTPRequestHandler`**（更灵活）。排除：那插件就要
   自己处理 HTTP 细节，而"写对分块传输"这件事我们已经错过三次——不该要求
   每个插件作者都踩一遍。
4. **面板/显示/路由合并成一个 `Surface` 字段**。排除：三者用途不同、出现频率
   不同（面板最常、路由最少），分开更清楚；`Surface` 已经是它们的容器。

## 后果

- **收益**：**加一个"有页面 + 有事件 + 有端点"的插件，壳一个字节不用改。**
  测试里现造了三个第三方插件分别验证（声明 display → 事件自动渲染；
  声明 route → 端点自动可用；卸载 → 都消失）。
- **实测（浏览器，真实 API）**：`/compact` 走插件自述的路由 → 折叠徽标按
  `fold` 渲染器画出「⟳ 上下文已压缩：折叠 2 条消息（约 1,936 → 97 tokens）」
  → 收尾帧按 `status` 渲染器更新状态栏；对话本身照常。
- **可度量的改进**：`plugins/webui.py` 里 compact/approval 的提及从 10 处降到
  **0 处**（只剩 docstring 举例）；`app.js` 从 17 处降到 5 处，且**全是审批交互
  + CSS 类名**（有意的边界），业务事件名与帧名归零。
- **约束与已知边界**：
  1. 渲染器只有四种，壳的能力边界到此为止（这是设计，不是缺陷）；
  2. 路由只支持 `GET`/`POST` 与单段 `<名字>` 捕获（不做正则/通配——插件的端点
     模式应当简单到一眼看懂）；
  3. 壳仍内置三条**通用**路由（ledger / sessions / send），它们与任何插件无关；
  4. 审批是唯一"壳认识具体交互"的地方——因为它是安全底座的一部分。
- **债务与后续**：如果将来出现"需要流式渲染的非插件场景"，可以考虑把
  `FrameWriter` 的形态再抽一层；目前只有插件端点在用。
