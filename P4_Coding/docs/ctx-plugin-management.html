ctx 如何管理插件

一次操作（装载、卸载、停用、提供一项服务）不会只改一个插件。它把世界推到 稳定态：依赖不满足的活动插件退位，依赖满足的等待插件激活， 相关 effect 逐层回卷。下面的 15 步重演了这套机制，点击任意插件可以看它此刻的 状态与回卷内容。

一、生命周期只有四种状态

pending → 依赖齐 active → 依赖走 pending
active → disable disabled → enable pending
pending → setup 抛错 failed → enable pending

load_plugin 返回时插件可能还在 pending——这不是错误，而是“等依赖”。真正的判断在 settle()：把世界反复推到稳定态。

二、settle 是一个循环

每次 provide / retract / load / unload / disable / enable 之后都会调用它。

while True:
    活动插件里依赖不再满足的 → 退回 pending
    pending 里依赖已经齐的   → 激活
    动态注入：先停不满足的，再启动已齐的
    if 这一轮没有任何变化:
        break

激活永远发生在干净的顶层：若当前正在装载某个 effect（_stack 非空）或已经在 settle 中，本次直接返回，由外层收尾时再扫一遍。

三、卸载是“深的先退”

提供者离开时，先算出依赖它的活动插件（服务闭包，按层扩展），反转顺序后逐个退位， 最后才回卷提供者自己。这样每个插件跑清理代码时，它依赖的服务都还在。 

plugin:tools
  └─ effect 子节点（动态注入 / 嵌套）
  └─ 退订事件
  └─ 撤销提供的服务
  └─ setup 返回的清理

回卷顺序：子 effect 先；同级 LIFO。
某个清理抛错不打断其余回卷，最后重抛第一个。

停用（disable）与卸载的区别只有一个：登记留在台账，enable 用同一个实例重跑 setup，配置与身份都不丢。

四、两种协作通道，一种回卷纪律

插件之间只有服务与事件两条行为通道；类型与纯函数可以单向依赖基座 （capability → base），兄弟能力之间不互相 import。 

class Reporter:
    name = "reporter"
    inject = ("sessions",)      # 必需：缺了 → pending
    optional = ("approval",)    # 可选：缺了 → 照常激活

    def setup(self, ctx):
        ctx.provide("report", ...)    # 注册即回卷
        ctx.on("session/event", ...)  # 注册即回卷
        ctx.inject(["llm"], self.attach_llm)
        # 依赖出现才运行；依赖消失自动拆

三条不变式：fail loud、不留半装、回卷干净。每次有效变更 revision +1， 判定方式是操作前后的状态签名对比。
