# _04_Context_Meter —— 上下文仪表（容量 / 构成 / 缓存命中）

P3 第 4 阶段（对应 [PLAN.md](../PLAN.md)）。**本阶段只加一个机制**：

> 一张"上下文仪表"：窗口容量、用了多少、**用在哪**（消息 / 系统工具 /
> 系统提示词 / 其他）、**前缀缓存命中率**；独立页面 + 挂到主界面顶栏。

**状态：✅ 已完成（2026-10-14）**

## 为什么先做仪表（而不是直接做压缩）

压缩要回答"什么时候压、压多少、值不值"，这些都需要**先看见**：占比告诉你
"是哪类内容在吃上下文"（实测：工具说明书占 77.6%），缓存命中率告诉你
"重发历史的实际成本有多高"（命中部分便宜得多）。所以 PLAN 里把仪表插到压缩
之前——**先有表盘，再装刹车**。

## 三个问题怎么答

**① 容量与使用**：分母是 `--context-window`（默认 64K）；分子优先用**实测**
（上次调用响应里的 `usage.prompt_tokens`——"模型这次真看到了多少"），
没有实测时退回字符估算，页面上如实标注来源。

**② 用在哪（四类构成）**：没有 tokenizer（不引依赖），按 DeepSeek 官方经验比例
估算（中文 ≈ 0.6/字、其他 ≈ 0.3/字符），把请求拆成四类：

    消息        user / assistant / tool 消息（含工具参数与结果）
    系统工具    工具说明书（名字 / 描述 / JSON Schema）      ← 实测占 77.6%
    系统提示词  system 正文（每 step 重渲染后的那一份）
    其他        角色标记与聊天模板开销

**四类估算按比例缩放到实测总额**（余数给最大项）——占比来自估算、总量来自实测，
所以"四类之和恰好 == used"是硬断言。

**③ 缓存命中率**：`Σhit / (Σhit + Σmiss)` **加权平均**（不是各次算术平均——
那样小请求会和大请求等权）。provider 不报缓存数据时显示"—"，不假装 0%。

## ⚠️ 调研发现（重要，交给 `_05` 压缩阶段）

**前缀缓存与"每 step 重渲染系统提示词"存在冲突**：实测确认 DeepSeek 的上下文
缓存要求**前缀稳定且足够长**才命中——

| 场景 | prompt | hit | miss |
|---|---|---|---|
| 固定系统提示词（160 tokens） | 160 | 0 | 160 |
| 固定系统提示词（1112 tokens，第 2 次） | 1112 | **896** | 216 |
| 系统提示词含变化的时间戳（每步重渲染） | 167 | 0 | 167 |

我们的 harness 每 step 重渲染系统提示词（含 `{{time}}`）——**前缀第一个字节就变了，
缓存永远不可能命中**。这条是 `_02`（每 step 渲染）与缓存友好性之间的真实张力，
`_05` 压缩阶段应当处理（可行方向：把易变内容移到前缀之后、或按"变化才重渲染"
进一步收紧粒度）。当前账本如实记录 0% 命中，不掩饰。

## 验收（对照 PLAN.md）

- [x] 构成估算能按实测总额缩放，**四类之和 == used**（硬断言）
