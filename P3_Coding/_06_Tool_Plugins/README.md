# _06_Tool_Plugins —— 工具插件化：拆开写、能开关、可自装

P3 第 6 阶段（对应 [PLAN.md](../PLAN.md)）。**本阶段只加一个机制**：

> 把"工具面"拆成**底座 + 工具插件**：底座只提供空的注册表与管理面，
> 每件（类）工具独立成插件、互不依赖；人在管理面板里停用/启用/卸载它们，
> **模型也能从工作区写一个新工具插件并装上**（经人工审批）。

**状态：✅ 已完成（2026-10-16）**

## 为什么这样设计

### ① 拆的是"底座"与"内容"，不是把文件拆细

`_01`–`_05` 的 `plugins/tools.py` 是个**合体插件**：它 `inject fs`，然后在
`setup` 里注册八件工具（计算、读写、检索、命令）。于是两件事被绑死了：

- **工具面是地基**（agent 依赖它，没有它模型没有手）；
- **工具内容是策略**（给不给模型命令执行、要不要检索，是装配方的取舍）。

合体的后果很实在：想少给一件工具，只能改代码；想加一件，得把新工具塞进同一个
文件；而"换个文件系统"（fs 插件的正常操作）会把**整个工具面**一起拆掉——
因为 tools 不得不 `inject fs`。

现在两层是：

    plugins/tools.py      底座：空注册表 + `tool-admin`（台账/开关）+ 两件自我管理工具
    plugins/tool_*.py     内容：各自 inject tools（+ 自己需要的能力），
                          往这个空注册表里登记自己的工具

拆完三个直接效果（正是用户提的三条诉求）：

| 诉求 | 落点 |
|---|---|
| 工具插件之间**解耦** | 它们只共同依赖 `tools` 服务与各自的能力插件（fs / subprocess），互相不调用、不依赖；装卸任一都不牵动别人 |
| 用户能**管理**工具 | 管理面板多一个「工具」标签页：按 owner 分组的台账 + 停用/启用/卸载 |
| AI 能**自己写工具** | `install_tool`：从工作区的 `.py` 装一个新工具插件（先人审源码，再装载） |

### ② 停用 ≠ 卸载：两个动作各有用途

    停用/启用   登记与实现都留着，只从**可见面**撤掉（模型看不到、也调不到）
    卸载插件    把提供它的那个插件整个撤掉，工具跟着回卷（要回来得重新装）

为什么都要有：**停用**是"这次先不给它用"（试一个新工具的效果、临时收紧危险
工具），代价小、随时开回来；**卸载**是"我不要这个能力了"，作用在插件上
（工具来自插件，只撤工具会留下一半的插件）。所以管理面板上每件工具都显示
**署名**（`owner`：哪个插件给的），卸载按钮落在那位 owner 上。

> 停用为什么不做成"卸载后重装"：重装等于把插件整个重来一遍（还会牵动依赖链），
> 而"停用"应当只影响可见面那一处。开关因此放在注册表上（`set_enabled`），
> `resolve()` / `visible()` 跳过停用的——对循环来说**停用 = 这件工具不存在**，
> 而不是"调用了才发现被拒"。

### ③ 登记必须署名（owner 必填）

`ToolRegistry.register(...)` 的 `owner` 是**必填**参数，漏写当场报错。这不是
洁癖：管理面板按它分组、"卸载这件工具"要知道该卸谁、审计要能回答"这工具哪来的"。
把约定变成不变量（决策 0031 的取向）——留个空字符串等着事后猜，就是给自己
埋一个静默的坑。

### ④ `@tool`：一件工具只写**一个函数**

写工具原本要三样东西凑齐：参数模型（pydantic）+ 定义（`define_tool`）+ 实现。
对"模型自己写工具"这条路来说，出错面太大——模型要同时写对三处顺序与名字。

`components/tools/declarative.py` 把它压成一处：

    @tool("word_count")
    def word_count(text: str) -> dict:
        """统计文本的单词数（按空白切分）。"""      # 文档串即工具说明
        return {"words": len(text.split())}

    签名 → JSON Schema（类型/必填/默认值都从签名读）
    文档串 → description（给模型看的说明）
    返回值 → 工具结果（错误也用 {"error": ...}，不抛异常）

**认不出的写法当场报错**（不支持的注解、`*args`、漏注解）：宁可让写工具的人
立刻看到"这里不行"，也不要静默产出一个 schema 与实现不一致的工具——那样的
工具会在真实调用时才炸。

### ⑤ 从"源码 → 插件"这件事提到内核（`kernel/loader.py`）

`_01` 把这段逻辑埋在 `self_tools.py` 的私有函数 `_plugin_from_source` 里。到了
`_06`，**装一个工具插件**也要点这把火，于是它有了第二个消费者。留在 self_tools
里就等于说"没有 self-tools 就不能装工具插件"——而工具插件是独立的一类东西。

放内核的理由：它**纯机制**——不认识任何插件名、不依赖任何服务（判据与
`kernel/plugin.py` 读声明那组纯函数一致）。策略（白名单、审批、从哪读源码）
留在插件层。

### ⑥ 管理面板：一个弹层，标签页由插件自述

`_05` 收尾把插件台账做成了独立弹层，但那一页是**壳里写死的**：入口、取数地址、
字段名、卡片画法全在 `app.js`。`_06` 要让"工具管理"也进同一个面板，再写一页
就是**第三次改壳**——"完全插件化"在展示层又成了假账。

于是补上第四条界面自述 `AdminSpec`（决策 0032 的同类）：

    插件声明：key / label / title / 取数地址 / 动作地址模板 / 页脚说明
    壳只做四件事：画标签 → GET 快照 → 按通用形状画卡片 → POST 动作

壳里现在没有任何具体管理面的名字（测试钉住："app.js 里不许出现 api/plugins /
api/tools"）。**降级规则是 replace-by-key**：壳内置一页只读的「插件」（直接读
内核台账，不依赖任何插件）；装了 plugin-admin 就用它的同 key 页顶掉内置页——
于是"没装插件管理"时界面退回只读，而不是空白或报错。

**快照每轮重取**（踩过的坑）：最初写成"每个标签页只取一次"（`loaded` 标记），
后果是**模型刚装上的工具永远不出现在面板里**——实测里工具面已经 16 件了，
面板还停在 15 件，连筛选都搜不到。管理快照是只读 JSON、本机请求，重取代价
可忽略。

### ⑦ 审批看什么，由工具**自己声明**

审批卡片要能把"人正在批准的东西"摆出来。原先的预览在审批插件里写死了一张
工具名清单（只有 `install_plugin` 有预览），`_06` 新加的 `install_tool` 不在
清单里 → **审批卡片空着**。浏览器实测当场看到：模型要装工具，理由下面一片空白。

修法：`ToolDefinition.review_path_arg`（"审批时看哪个参数指向的文件"），
审批插件按声明读文件。**少一张需要人工同步的清单。**

## 验收形状

- **解耦**：装卸任一工具插件，别的工具插件登记与可用性不受影响；
  换 fs 时只有真正依赖 fs 的工具插件退位（工具面与 agent 照常）；
- **管理**：停用后模型**看不到也调不到**（`resolve` 返回 None），登记仍在、
  一键开回；卸载插件连带其工具一起回卷；管理面板的"可安装"格子随状态增减；
- **自装**：`install_tool` 装出的工具出现在工具面、带 owner 署名、下一轮可调用；
  没有审批策略时 fail-closed 拒绝；源码里写成类/工厂/实例三种形态都能装；
- **壳零知识**：管理弹层的标签、地址、按钮全来自自述；没装任何管理插件时
  退回内置只读页；
- **门禁**：`ruff` + **406 用例**全绿（其中 `_06` 新增 47 条）。

## 实测记录（浏览器，2026-10-16）

在真实浏览器里把三条路都跑了一遍（`--web --realtime --self-tools`）：

1. **面板**：打开管理弹层 → 两个标签页（插件 / 工具）→「工具」页按 owner 分组
   15 件工具，带"需审批"标签；
2. **开关**：点 `calculate` 的「停用」→ 卡片翻成"已停用/启用"，
   `/api/ledger` 的工具面**立刻少一件**（15 → 14）；「启用」后回来；
3. **装卸**：点「卸载插件」→ 回执"已卸载插件 tool-calc（连带 1 件工具：calculate）"，
   卡片消失、`tool-calc` 变成"可安装"虚线格子；点「安装」→ 工具回来；
4. **模型自装工具**：对模型说"给自己加一个 word_count 工具"→ 它自己
   `list_tools` 看规范 → `write_file` 写 `plugins/word_count.py`（**审批卡里
   能看到源码全文**）→ `install_tool` 装载（第二次审批）→
   下一轮它真的调用了 `word_count("one two three four five")` 并答"5 个单词"。

**实测挖出并修掉的三个真 bug**（每个都补了回归测试，且都反向验证过）：

| # | 症状 | 根因 |
|---|---|---|
| 1 | 页面报"初始化失败：ledger is not defined" | 重写弹层时删掉了旧的 `ledger` 状态对象，渲染函数里还有三处引用；静态检查与 pytest 全绿（只查字符串/DOM id）→ 补"桩 DOM 整页冒烟"用例 |
| 2 | 模型写的插件装不上：`setup() missing 1 required positional argument: 'ctx'` | `kernel/loader.py` 的入口判据是 `callable(obj) and not hasattr(obj, "setup")`——**类对象本身有 setup 方法**，于是类被当成实例直接交给内核。判据改成"是类就必须实例化" |
| 3 | 模型刚装上的工具在管理面板里搜不到 | 管理快照写成"每个标签页只取一次"，面板锁死在打开时的内容；改为每轮重取 |

另外顺手修掉一处**盲批**：`install_tool` 的审批卡片原先没有源码预览
（预览清单里只有 `install_plugin`）——改成工具自己声明 `review_path_arg`。

## 与 `_05` 的差异（一句话）

`_05` 的 tools 是"**工具面**"（底座与内容合体）；`_06` 把它拆成
"**工具面底座** + 各自独立的工具插件"，并让这个面**看得见、管得着、
能被模型自己扩展**。

## 已知边界

- **停用不跨重装**：停用状态跟着登记走（卸载插件再装回来 = 工具可用）。
  这是刻意的：停用是"这次先不给"，不是持久配置；
- **`install_tool` 只读工作区内的 `.py`**：走 fs 服务（沙箱边界之内），
  且必须有人批准；模型给的是**路径**不是代码；
- **管理面板的"安装"不经过审批**：人亲手点的那一下，本人就是审批人
  （与 plugin-admin 同一原则）。审批拦的是**模型发起**的那条路；
- **工具插件的顺序即面板顺序**：`owners()` 按登记顺序，没有"重要度"概念；
- **`list_tools` / `install_tool` 属于底座**（owner="tools"）：它们是工具面的
  自我管理，停用它们等于半关工具管理——面板允许（它是你的应用），但要自己
  想清楚。
